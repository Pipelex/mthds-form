# The generative layer

`@pipelex/mthds-form/generative` renders a **layout**: a data file, written once for a method, that says how that method's page should look. It is the third entry point, it is optional, and a host that never imports it pays nothing for it.

The reason it is a separate entry rather than a feature of `./react` is the [dependency budget](dependency-budget.md): a layout is compiled and validated, which costs json-render and zod, and a host rendering an ordinary form should not carry either.

The layer is two entries. **`@pipelex/mthds-form/generative/headless`** is everything that renders nothing: the catalog and the frames, the designer method's catalog data and brief, the prompt pin, the seed's line, the JSONL compiler, the two checks and `layoutCheckProblems`, the state paths, `payloadToState` and the provenance record. It carries no React and no `'use client'` directive, so it imports alike from a server component, a server action, a route handler, a worker, a script and a browser. **`@pipelex/mthds-form/generative`** renders: it re-exports all of the headless entry beside the page, the registry and the providers, behind a `'use client'` directive. A client host imports from `./generative` alone; a host's server imports `./generative/headless`, because every export of a client module reaches a React Server Components server as a client reference that throws when it is called. Every function this document names that renders nothing is exported by both.

## Three artifacts, and what each is allowed to say

| Artifact           | Who makes it                             | What it states                                                               |
| ------------------ | ---------------------------------------- | ---------------------------------------------------------------------------- |
| The **descriptor** | this package's kernel, from the method   | what every input and result field _is_ — kind, requiredness, bounds, choices |
| The **layout**     | a model, once per method version         | which path goes where on the page, in what component, with what copy         |
| The **state**      | the person filling the form, and the run | two JSON trees, `/inputs` and `/result`                                      |

The line between the first two is the package's first rule, and it is the whole design: **a layout names a path and nothing more.** It does not restate a field's kind, its requiredness, its enum, or its bounds — it says "put `/inputs/request/city` in an `Input` labelled City, in the second section". Everything a page needs to _know_ still comes from the descriptor, derived fresh from the method every time it is read. That is what makes a layout safe to store: it cannot go out of date about facts it never stated.

Nothing here calls a model. The two things that do — producing a layout, and running the method — are the host's, on either side of this seam.

## The wire format

A layout arrives as **JSONL**: one RFC-6902 JSON patch per line, root first and parents before children, so a renderer can paint a partial tree at every line while a model is still streaming. A stored layout is that text exactly as it was emitted; a host compiles it before it validates it.

Compiling is the first thing that touches untrusted text, and it happens before either gate can return a verdict, so it defends itself rather than relying on one. `specFromJsonl` applies the patches a line at a time: a line whose path would walk onto a prototype is dropped — and so is one whose `from`, on a `copy` or a `move`, would, since the applier copies a reference rather than a clone and a later line can then reach the prototype through a perfectly ordinary path — and so is a line the patch applier refuses. What survives is a partial spec the two gates then judge on its merits — which is a verdict a host can act on, where a throw would have arrived instead of one.

```ts
import { specFromJsonl, specToJsonl, jsonlLines } from '@pipelex/mthds-form/generative';

const spec = specFromJsonl(storedLayout);
```

Keeping the JSONL rather than only the compiled spec is deliberate: it is the producer's actual output, and it is what a regression is read against.

## The two checks, and the fallback rule

A host runs both before it renders, and falls back to the kernel's plain form if either says no.

```ts
import {
  PROMPT_HASH,
  formatProblems,
  layoutFits,
  validateAgainstCatalog,
} from '@pipelex/mthds-form/generative'; // or '@pipelex/mthds-form/generative/headless' on a server
```

**`validateAgainstCatalog(spec)`** asks whether the layout is written in the vocabulary of a whole page (a frame's layout passes `frameCatalog(frame)` as the second argument; the exported `catalog` defines every frame's components too, so it is what the registry renders, not what a page may hold): every element type known, every prop declared and correctly typed (an expression may stand anywhere inside a prop, a whole entry of a list included, because json-render resolves it wherever it sits, so the typing reads past it rather than refusing the object it stands for, while a prop whose values are a fixed set takes a literal alone), one panel per tab or step, exactly two children in a `Split` or a `Workspace` (their renderers lay out two and would drop a third in silence), no empty option in a choice (no dropdown row or pill can offer nothing, and the run gate would refuse whatever a renderer wrote in its place), no heading level skipped and exactly one h1 — counting what the components render, since the a11y gate reads the DOM and not the element types: a `Hero`'s headline is the h1, a `Section`'s or a `Rail`'s title an h2, a titled `Card`'s an h3 — at most one of a component that renders as one of the page's landmarks (an `AppBar` is its banner, a `Footer` its contentinfo), every element reachable from the root, no element its own descendant, and the element tree no deeper than this entry renders. What a component renders beyond its schema is not read off its name: the catalog carries it as `renders`, a table of `ComponentRendering` per component — the heading its title is, the landmark it renders as, the fixed number of children it lays out, the prop whose entries are its panels — declared as `COMPONENT_RENDERINGS` beside this entry's definitions and read off whichever catalog the validator is handed. A host validating a vocabulary of its own declares what its renderers do, or nothing, in which case it is held to its schemas and its `Heading` elements alone, and asked for an h1 only when its vocabulary can render one. It answers with problems, not exceptions — `formatProblems` renders them for a log — and that holds for a spec malformed in ways json-render's own walk throws on, because a host calling this to decide whether rendering is safe has no use for an exception.

The depth cap is there for the same reason and is worth knowing about: every walk in the gate recurses, so without it a deep enough chain overflows the stack inside the check, and whether it does depends on the engine rather than on the layout. A stored artifact should get one verdict wherever it is checked, so the limit is the entry's rather than the stack's.

It also reads the `on` field, which says as much about a page as its props do. Every action a layout binds must be one the catalog or the runtime has, and every event it binds must be one the component's definition declares it emits — an action nothing handles, or an event nothing fires (`on.click` on a `Cta`, which emits `press`), renders a button that does nothing, and a page whose only call to action is dead validates perfectly otherwise, so nothing else would catch it. And a layout may **not write into `/inputs` or `/result`**: every destination a state-writing action names is refused there — `setState`'s, `pushState`'s and `removeState`'s `statePath`, but also the `statePath` `validateForm` writes its verdict to and the `clearStatePath` `pushState` empties after it appends — because those two trees are the host's: `/inputs` filled by the person through the controls and by `seedInputs`, `/result` by the run. A destination is judged as the runtime will read it, which supplies a missing leading slash rather than refusing the path, and it must be a literal, never an expression. And the ban reads every place a binding can sit, not only `on`: a `watch`, whose bindings fire when the state at its key changes with no event and no person in between, and the `onSuccess` and `onError` of any binding, whose `set` writes each key straight into the state with no handler between and whose chained `action` is a binding of its own, held to the same name check and the same ban as far as the chain goes. And a run is billed, so the validator lets one start from a deliberate gesture alone: a `run` is accepted directly under `press`, a button's, or `submit`, which is Enter in a field and how a plain form submits, and refused under every other event, since `change`, `focus` and `blur` fire as the person edits or moves through the page; under a `watch`, which fires with no gesture at all; and anywhere in a chain, since json-render applies a chain after a handler alone, so a run chained after `validateForm` never fires and one chained after a run starts a second billed run as the first settles. A layout that could write a value into the run payload would be stating a value rather than naming a path, which is rule 1 inverted. Scratch state of the layout's own, at any other path, is its business.

**`layoutFits(descriptor, spec)`** asks whether the layout still fits the method, in three directions:

- _Staleness_ — every path the layout **mentions** is a path the descriptor still has. A method renames an input and a delegated path resolves to nothing while a bound path writes into a corner of the state the run never reads. Neither fails loudly on its own. Mentioning covers every form the prompt teaches, not just the binding: the `path` of a hatch, `{ "$bindState": … }`, `{ "$state": … }`, the condition inside a `$cond`, the interpolations in a `$template`, the element's own top-level `visible` condition, the list a `repeat` lays out — resolved through the repeats above it when it is written relative — and, inside a repeat, the item-relative `{ "$item": … }` and `{ "$bindItem": … }`, resolved against the repeat's list the same way, so a renamed member of a repeated item is as stale as a renamed input and a `$bindItem` under `/result` is as refused as a `$bindState` there; one outside any repeat resolves to nothing and is refused as such. The `visible` one is why the list matters — a `visible` comparing against a path the method no longer has never holds, so it hides its element for good, and a required input bound inside it still counts as offered while nobody can see it. The `repeat` one is the same silence on a result page: a repeat over a list the method renamed renders nothing, and there is no coverage on that side to miss it. A repeat over a path that holds something other than a list is refused too, saying what the path holds: json-render maps over what it reads there, so a text throws in the render of the element above and drops its whole subtree, and a structure renders nothing. Only paths under the tree the descriptor owns are asked about, bound or read; a layout's own scratch state — a `Switch` bound to `/ui/showDetails` to drive a `visible` condition, say — is its business. The one binding no page may make is into `/result`, which the run fills: `layoutFits` refuses it as the validator refuses a `setState` there.
- _Shape_ — a `Grid` whose only child carries the `repeat` is refused. json-render renders a repeat's element once and that element's children once per item, so such a Grid is one cell holding every item in a column — three slide directions in a third of the page, the rest empty — while the layout validates perfectly. The repeat belongs on the Grid itself, with the item's element as its child, and the problem says so in those words for the repair pass.
- _Coverage_ — every path the descriptor **requires** is one the layout offers somewhere: bound to a control, laid out as a repeat, or delegated at that path or an ancestor of it. A layout that simply omits a required input is not stale and validates perfectly; it renders a page the person cannot complete, and the run gate then refuses the run for an input with no box on screen. A structure counts as covered when what it _requires_ is covered, so a layout may still leave out an optional member.
- _Kind_ — every path the layout **shows** as a value is a scalar, and every path it reads into a prop that takes a list is a list. A `SummaryRow` whose `value` read `/inputs/document`, a structure of a url and a filename, was not stale and validated perfectly, and rendered `[object Object]`, because the renderer stringifies what it is handed and only the descriptor knows what kind a path is. A `$state`, an item-relative `$item` or an interpolation of a `$template` sitting in a prop is refused when the path is an `object`, a `list`, a `document` or an `image`; a condition is left alone, since a `$cond` or a `visible` only asks whether a value is set. The props that take a list — every array-typed prop of the catalog, read from its schemas, and the rows a `DataTable` lays out — are held the other way round: written as one expression, the path must be a list, since a renderer maps over what it is handed and a structure there renders nothing while a text throws, and where the prop's items are values (an `AppBar`'s links, a `Steps`' names) a list of structures is refused too; written as an array literal, each entry is a value and is judged as one. A binding sitting in such a prop is held to its path's kind as a read is, since it reads the path it writes, and a `$template` there is refused outright, since it writes a text and never a list. An interpolation is resolved the way the runtime resolves it: `${/result/amount}` as written, a bare `${name}` through the item of the repeat above the element, and outside any repeat off the root of the state.

Like the validator, it answers with problems and never throws, whatever shape the layout arrived in: a malformed spec is one line naming what the walk tripped on. The two are exported separately and a host may run them in either order, so neither assumes the other refused the shape first. `layoutCheckProblems`, which runs both for a frame, keeps the same promise over its other arguments, because a host calls it on a layout and a frame it stored and read back: a frame this package does not draw is one line rather than a check against no vocabulary at all, which used to exclude nothing, a missing descriptor is one line, and anything that is not a spec, `null` included, is one line rather than an exception.

The **prompt hash** is the third condition and the cheapest. `PROMPT_HASH` is the first twelve hex digits of the SHA-256 of `promptHashSubject(method)`: the designer method's text, a newline, then the JSON of every frame's catalog data in `FRAMES` order (`page`, `composer`, `result`) — what a run is actually given, so a reworded rule and a renamed prop each move it, whichever frame the prop belongs to; every stored layout records the hash it was produced against. The recipe is exported so a host that stamps the layouts it stores computes the same twelve digits from the method file it sent, and `src/generative/__tests__/prompt.test.ts` holds the pin to it. A layout whose hash is not this one is not rendered, because the vocabulary it was written in is no longer the vocabulary this entry renders. It is a pinned constant rather than a computation, so the entry stays importable from a browser and a host can compare it synchronously.

So the fallback rule, in full: **the kernel's plain form renders when there is no layout, a stale prompt hash, an invalid layout, `layoutFits` false, or a render error.** A produced page is an enhancement over a form that always works, never a replacement for one.

A layout written for one of a host's frames (below) is checked against that frame's vocabulary rather than the whole catalog's, and `layoutCheckProblems(spec, { frame, descriptor })` runs the two checks in one call: the frame catalog's verdict (`frameCatalog(frame)`) then `layoutProblems(descriptor, spec)`, one problem a line. Between the two it asks one thing neither check can: whether a page or a composer that takes inputs binds the `run` action directly under some element's `on.press`, as the binding or as one entry of a list of them, since a layout whose only call to action never runs the method validates perfectly and renders a dead page. In the composer frame the one control that emits `press` is the `Composer`'s run button, so that button must run; a run under a field's `submit` is a deliberate gesture the catalog check accepts, but Enter in a field is no control anyone can see, so it does not stand in for the button. A layout that checks the form first writes `[{ "action": "validateForm" }, { "action": "run" }]`, which runs in order. An empty list means the layout may render; anything else means the plain form, and the same lines are what the method's repair pass reads.

## The two escape hatches

A catalog cannot render everything a method can declare — a file upload, a date, a document, prose, markup. Rather than approximate them, a layout hands them back:

- **`MthdsField`** at an `/inputs/...` path renders the kernel's own control for that field.
- **`MthdsResult`** at a `/result/...` path renders the kernel's own read-only view of that subtree. A file inside it carries its own download button and saves under the name the whole-result download gives it, because the hatch places the subtree at its path in the result (see [result-view.md](result-view.md#a-files-own-download-button)).

Each takes a `path` literal and nothing else. That is what keeps rule 1 intact: the hatch does not describe the field, it points at it, and the kernel reads the descriptor as it always does. Inside a repeat the path is relative to the item, which is how one subtree of every item is delegated.

## Rendering a page

```tsx
import { GenerativePage, seedInputs, payloadToState } from '@pipelex/mthds-form/generative';

<GenerativePage
  spec={spec}
  store={store}
  scope={{ inputs: fields, env }}
  brand={manifest}
  onRun={(state) => start(state)}
  loading={streaming}
/>;
```

`brand` is the manifest the product chrome renders — the app bar's logo pair and name, the web font — and this entry's own registry needs one, because a layout that opens with an `AppBar` has that component read the brand in scope. Without one it throws, and what a host sees is quieter than a thrown render: json-render wraps each element in a boundary that catches the throw, so the bar is simply missing from the page, with the cure named in the error the console reports. The page puts the manifest in scope itself when it is given one; a host may instead wrap the tree in `BrandProvider`, and a host rendering a registry of its own with no brand components may pass nothing. The bar the `AppBar` draws is exported as `BrandBar` (`app`, and optionally `links` and `tag`), for a host to draw as its own chrome inside a `BrandProvider`: over the plain form, which draws no brand mark of its own, or above a designed page whose layout has no app bar, rather than building a one-element spec and a second page for a header. The manifest is one half of a brand; the other is the token stylesheet a host puts on the page's root, and both are validated and compiled by the `./brand` entry ([brand.md](brand.md)).

The store is **controlled**: the host creates it, seeds it with `seedInputs` (which seeds only the defaults the method authored, and leaves an optional structure with no default of its own absent, closed behind its optional disclosure), and reads it back to start the run. So what the page writes is exactly what the kernel's readiness is computed from, and generation is nowhere in the request path. `onRun` may be an inline closure over the host's own state, as above: the page calls whichever one the latest render passed, over whichever store it passed — json-render registers its handlers once at mount, so the page keeps its one handler stable and routes it to the current pair itself. `payloadToState` loads what a run returned into the `/result` tree — a date arrives in the serializer's typed envelope and a plural result as `{items: [...]}`, and this is what turns both into what a layout binds to.

`onRun` is called with the store's state when a run button is pressed, one run at a time: when it returns the run's promise, or any thenable, a press while it is pending starts nothing, so a host that holds the button only after an await (its `env.disabled` arriving a render later) cannot start a second billed run. The guard outlasts the settled run by one task, the task in which json-render applies the binding's `onSuccess` or `onError` chain, so a layout rendered past the catalog check with a run chained under its own run still starts one run per press.

`scope` is what the escape hatches resolve against: `inputs` for an input page, `result` for a result page, plus the `env` the controls need (upload, disabled, a storage resolver) and an `idPrefix` when two pages share a screen.

A page reads the presentation it is mounted in (`FieldPresentationProvider`, [architecture.md](architecture.md)), as the kernel's own controls do, and a host rendering a method app mounts it in `app`. That decides how a choice reads. A layout's `Select`, `Radio` and `Segmented` are meant to take their `options` as the brief's choices spelled exactly, because each writes the option it shows, unchanged, and the run gate refuses a value the enum does not declare; the catalog's validator checks only that no option is empty, so copying them exactly is the producer's to keep. Each control shows each option as the kernel words it: `keynote` reads "Keynote" in `app` and stays `keynote` in `studio`, the very rule the kernel's own choice control and the result view follow, collision fallback included ([result-view.md](result-view.md#labels-and-enum-values-follow-the-presentation-exactly-as-the-form-does)). The descriptor carries no display label and the standard is not asked for one, so the model is never asked to write one either: a label a layout authored could disagree with the value it writes.

**Every control the layer draws is a finger's size on a phone**, as the kernel's are ([architecture.md](architecture.md), "Below Tailwind's `sm` breakpoint"). The number input and the select are 44 pixels tall at every width, as the layer's text input and button beside them always were, and so are a journey's Back and Next. Below `sm`, a segmented choice's options and a tab grow to 44 by 44 pixels, however short their label, a row of tabs wraps rather than pushing the page sideways, and a native radio or check box keeps its 16 pixel box while the label row it sits in grows to 44 pixels across the column: a tap anywhere on a label activates the control it wraps, so the row is the target, and the rows of a radio group then sit with no gap between them. From `sm` up those keep the size they had. Before this the number input was 40 pixels tall, a radio or a check box offered a 16 pixel box and its 20 pixel line, and an option 36. `Generative/Trip planner` › "…, phone" and `Generative/Slide designer` › "…, phone" hold every control of a captured layout to 44 pixels at a 375px viewport (`onAPhone` in `layout-page.tsx`), and `expectTouchTarget` counts the label a native input sits inside as its hit area ([storybook.md](storybook.md)).

### Uploads, which arrive by a different id here

`env.onDropFile` is handed the DOM id of the field the file landed on, and on a generative page that id is not the dotted value path [the upload seam](upload-seam.md) describes for a plain form. `MthdsField` mints it from the store path it was given — `/inputs/request/city` becomes `gen-inputs-request-city`, with the `idPrefix` in front of it and the kernel's own `.`-joined suffix for a field nested inside the delegated one. `pathFromDomId` is the inverse, and it is what a host writes back through:

```ts
import { pathFromDomId } from '@pipelex/mthds-form/generative';

env = {
  onDropFile: (id, file) => {
    const path = pathFromDomId(idPrefix, id);
    if (!path) return;
    return upload(file).then((value) => {
      store.set(path, value);
      return value;
    });
  },
};
```

It returns the upload, a promise of the value it writes, so the field keeps the dropped file's preview for that value whenever the store's write lands ([the upload seam](upload-seam.md#the-local-preview-belongs-to-the-value-it-was-made-for)). A scope that takes a list's removals through `env.onRemoveItem` is handed the list's id minted the same way, and recovers the list's path with `pathFromDomId` as well.

Kept beside `domIdFor` in the same module so the two cannot drift, and exact for any name: the id escapes its own separator, so `/inputs/a-b` and `/inputs/a/b` do not mint the same one. That used to rest on an assumption about MTHDS names, which nothing in this package can enforce — a name reaches the descriptor from a JSON Schema property — and the cost of it being wrong was an upload written to a different, plausible-looking path with no error anywhere.

Which ways into a file value the page offers follows the same rule as a plain form, because `MthdsField` renders through `FieldRenderer` with the scope's `env`: a scope with no `onDropFile` gets a link-only file field rather than a dropzone that drops what it takes, and `allowUrl: false` takes the link away ([the upload seam](upload-seam.md) § "Which ways into a file value a host offers"). A scope that offers neither makes the field throw as it does on a plain form, but json-render catches the throw in the boundary it wraps around every element: the error, naming the field's id, is what the boundary logs, and the field renders nothing while the rest of the page stays.

## A host's frames: the composer and the result page

A layout may be a whole product page — its own app bar, hero, side panel and footer, the vocabulary above — or one moment of a host's **compose-then-result app**, where the host draws everything around the method and the layout fills the middle. That is the **frame** a layout is written for, one of `FRAMES`:

| Frame      | What the host draws                                                                              | What the layout places                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `page`     | nothing: the layout is the whole page                                                            | everything, from the product components                                                                                                     |
| `composer` | the band with the team's logo and the app's name; how long a run takes; what the run button does | a `Composer` — the page's headline, its lede, the inputs in one raised panel, and the action row at its foot — with `FieldGroup`s inside it |
| `result`   | the band, the request bar over the page, and what each of the result's actions does              | a `ResultHeader` — the page's title, with the host's actions beside it — then the result, in the result frame's own figures                 |

Each frame has its own vocabulary. `designerCatalog({ frame })` is what the designer method is handed, and `frameCatalog(frame)` what a layout is validated against: the composer keeps the inputs and leaves out every result component but `TextList`, which lays out a list of short texts such as what a run gives back, the result page keeps its figures and leaves out every input, and neither has the components the host already draws (`AppBar`, `Footer`, `Workspace`, `Rail`, `Cta`, `Hero`) nor a bare `Button`. `componentNamesFor(frame)` lists the names; `COMPOSER_COMPONENTS` and `RESULT_COMPONENTS` are each frame's own. A `Composer` set in two columns flows its groups down one column and on into the next, balanced, rather than in rows: a row as tall as its tallest group left a hole beside every long list. A group may continue into the next column between its fields, never inside a field and never right after a title: a list is one field, so its rows stay together under its label rather than leaving the last one alone at the top of the next column. Its panel is the host's panel, so with no style it is the host's hairline with no shadow, and its run button, like a whole page's `Cta`, is disabled while the host's `env.disabled` says a run is going, as the plain form's submit is. On a composer, a date and a list are delegated to `MthdsField` as on a whole page. On a result page the frame lays out what the whole page delegates: a picture through `Picture`, a date through `DateText` (a date with a time stays delegated, since `DateText` writes the day alone), a list of short texts through `TextList`, a share through `ProportionBar`, a palette through `Swatches`, and the rest through `Fact` and `Detail`. `Picture` reads a stored file the way the kernel's result view does — through the host's resolver (`useResolvedUrl`, from `ResultEnvProvider`) and then `viewableUrl`, which draws nothing for a URL a browser should not load — and a stored file the host cannot resolve falls back to its own public URL, as in the result view; it sends no referrer, as every picture the package draws does, and is named by the image's own caption when the layout writes no `alt`; `layoutFits` holds its `path` to an image the result has, resolved through the repeats above it, so a picture of a renamed member is refused rather than drawn empty. That holds only for a path written as it is, so `Picture` names its `path` literally, as a hatch does, and the validator refuses an expression there: one passed that check alone and resolved at render time to whatever it held. It holds a `ProportionBar` the same way: its `items` must be a list of structures, its `labelKey` a member of them and its `valueKey` a member holding a number, since a misspelt key would draw an empty bar. Parts written out inline, which the catalog takes as a list of anything, must each be a structure naming both members, so a `null`, a word or an expression standing for a whole part is refused, part by part. `ResultHeader` draws the host's actions only when the host hands it `onAction` as well, so no action button is drawn that does nothing.

What only the host knows travels beside the layout, never in it. `FrameHostProvider` hands the frame components the host's facts: `eta`, how long a run usually takes, which the `Composer`'s action row shows; `actions`, the result's actions primary first, which the `ResultHeader` draws; and `onAction`, what each does. The layout names where they go and the host fills them, so a stored layout never says "Takes about 30 seconds" about an app whose runs got slower.

The brief says which frame and which **style** a page is written for. `inputBrief(subject, fields, { frame, style, result })` and `resultBrief(subject, field, state, { frame, style })` take the frame (`page` when omitted) and an `AppStyleId` from the `./brand` entry. The brief then carries the style as data, its name and its one-sentence direction from `APP_STYLES`, and the method's `render_brief` lays out a Style section asking for a composition that reads as that style — how much air, how large a headline, how many groups — while saying the look itself, the faces, radii, panels and colour, is the components'. A composer's brief carries `returns` too, read from the result's own titles and descriptions when `result` is passed, so the page may say once what one run gives back. The style is a fact about the team, not the method, so a host that lets a team change its style designs that team's layouts again.

The **store** a host renders a layout over is json-render's, re-exported here so a host needs no second dependency to make one: `createStateStore`, with the `Spec`, `StateStore` and `StateModel` types. A composer's store holds `{ inputs }`, seeded with `seedInputs` or with the values a person is resuming; a result page's holds `{ result: payloadToState(field, payload) }`.

So a host rendering a stored layout for a moment, with the plain form as its fallback, does this:

```tsx
import {
  FrameHostProvider,
  GenerativePage,
  PROMPT_HASH,
  createStateStore,
  layoutCheckProblems,
  payloadToState,
} from '@pipelex/mthds-form/generative';

const usable =
  stored &&
  stored.promptHash === PROMPT_HASH &&
  layoutCheckProblems(stored.spec, { frame: 'result', descriptor: { result: field } }).length === 0;

usable ? (
  <FrameHostProvider host={{ actions: ['Download PDF', 'Share'], onAction }}>
    <GenerativePage
      spec={stored.spec}
      store={createStateStore({ result: payloadToState(field, payload) })}
      scope={{ result: field }}
    />
  </FrameHostProvider>
) : (
  <PlainResultPage field={field} payload={payload} />
);
```

Whatever passes the two checks renders without throwing, and that is a property of the renderers as much as of the checks. The checks hold `/inputs` and `/result` to what the descriptor says they are, but a layout's own scratch state is its business, and a prop bound to it resolves to whatever JSON a `setState` wrote there: a structure where a title belongs, a word where a list of options belongs. So every renderer this entry registers is handed its props held to the catalog's own declaration of them, once, in `src/generative/declared-props.ts`, rather than each renderer guarding each prop: a value its schema accepts is passed as it is; a number or a boolean in a text prop is written out, as an interpolation would write it; a list keeps the entries its item schema accepts; and anything else is absent, which is `null` where the prop is nullable and the empty text or list where it is required, both of which a renderer draws as nothing. A prop declared `any`, such as the value a `Fact` shows or the rows of a `DataTable`, is its renderer's own to read, and is written out through a function that never throws, even on JSON carrying its own `toString` member. `src/generative/__tests__/checked-renders.test.tsx` holds every component of the catalog to this, each open prop bound to scratch state holding each hostile value in turn, after asserting that both checks accept the layout.

A render error is the last condition, and json-render's per-element boundary catches it without failing the rest of the page, which is also why a boundary a host puts around the page never sees it: the element is dropped, the error is logged, and the page arrives incomplete with nothing for the host to act on. **`onElementError(error, { type, componentStack })`** on `GenerativePage` is how the page tells it. Every renderer of the page's registry is wrapped, once per registry, in a boundary inside json-render's, and the page's root gets one too, because json-render resolves an element's props before its renderer runs, so a throw there - a `$template` writing out JSON that carries its own `toString` member, say - is caught by the boundary of the element above, and the root has none. When the host passes the callback, the boundary catches the throw first, renders nothing in its place as json-render's would, and calls the host's latest callback after the commit, once for each element that failed, with the component type the element named (or, for a throw in a repeat over a payload that is not a list or in a child's props, the element above it). A host that wants the whole page to fall back sets its own state there and renders the plain view instead. When it passes none, the boundary throws the error on, so the page behaves exactly as json-render alone does: an element's throw is logged and dropped, and the root's reaches the host's own boundary around the page, which is why a host keeps one. The wrapping does not depend on the callback, so a host that starts or stops passing one remounts nothing. A failed element stays blank until the page is given a new spec, as json-render's own boundary leaves it; only the root's boundary tries again with a new spec.

## Producing a layout

The producer is outside this package, but the package ships what a producer needs, and all of it is in **`./generative/headless`**: a producer starts the designer method where its API key is, on its server, and checks the answer there before it stores it, so nothing it imports may sit behind the rendering entry's client directive. The catalog data, the brief, the concept names, the seed's line, the prompt pin and its recipe, the compiler, the checks and the repair bound are each imported from it, in a server action or a route handler as much as in a script; `./generative` exports the same values for a host that produces in the browser.

The **designer method** is the prompt. It ships as data at `@pipelex/mthds-form/layout-design.mthds`: a `.mthds` bundle whose main pipe, `design_layout`, takes three inputs — `catalog`, `brief` and an optional `seed`, the first two as data — and runs three stages. `render_brief` lays the brief out: a Jinja2 template over the brief's data, with no model behind it, whose Markdown is the text both model stages then read — so every sentence a model reads about the page, the headings, how a path line is worded, what "delegated" says, is in that file too. `plan_page` reads that text and the catalog and writes a `PagePlan`, a structure the bundle declares: what the page is for, its title and composition, its regions with the elements and paths each holds, what runs the method, the defaults and what is delegated. It alone sees the seed, because the plan is where two runs of the same brief diverge. Neither model stage prescribes a composition: the shape of the page is the planner's decision, written into the plan, and the prose names none of the product chrome — what a component is for travels in its catalog description, as data, the control that runs the method is named by the brief, as data, and a test holds the method to naming none — so two layouts of one brief may differ in their bones and not only in their copy. `emit_page` is handed the plan, the catalog with every props signature and the laid-out brief, and emits the JSONL patches. Every paragraph either model reads — the brief's own prose, the design direction and the planning rules on one side, the output format, the state contract and the numbered rules on the other — is authored in that file. It ships as a file rather than as a string baked into a module because it is still being iterated on — a newer method is then a package upgrade rather than a code change — and because nothing in the entry may read it, which is what keeps the entry importable from a browser. Improving the prompt is editing that file; nothing in TypeScript renders a prompt string, and nothing in TypeScript writes a sentence of the brief. Three things to know before editing it: a literal dollar sign is written `$$`, because `$name` is the language's inline substitution, so every json-render expression key in the prose (`$$state`, `$$bindState`, `$$item`, ...) is spelled that way, in the brief's template too; the component and action sections, like the plan the builder reads, are Jinja2 loops in the two prompts, which keep every newline they are written with, so a heading that follows a loop sits directly under its `{% endfor %}` to render one blank line rather than two; and the brief's template is a `markdown` template, whose category trims a line holding only a `{% %}` tag, so a line that ends with such a tag closes it with `+%}` to keep its newline, and every `{% set %}` sits at the top of the template — the runtime reads a name set inside a loop or a condition as an input the pipe never declared.

The **catalog as data** (`designerCatalog({ frame })`, the `page` frame's when called with nothing) is the `catalog` input: every component with its name, its props signature rendered from its zod schema (`{ label: string, value?: string }`, the shape json-render's own prompt uses), its description, whether it accepts children, its named slots and the events it emits — then every action, the runtime's four built-in ones first. The method lays both lists out itself, so a component added to the catalog appears in the prompt with no change to the method, while the rules and the direction that name components stay the method's own prose. The value travels as the content of a structured input, under the concept `DESIGNER_CATALOG_CONCEPT` (`generative.Catalog`), whose structure the method declares.

The **brief as data** (`inputBrief`, `resultBrief`) is the per-method half, projected from the descriptor and nothing else into the method's own `Brief` structure (`DesignerBrief`, sent under the concept `DESIGNER_BRIEF_CONCEPT`, `generative.Brief`): which page it is and for which pipe, every path flattened in reading order with its depth, its kind in words, its constraints in words, whether the kernel keeps it and what gates the run, the control that runs the method, and on a result page the state of one real run as JSON, so a model can judge magnitudes. The defaults it lists are the seeds, and they are the outermost default of each subtree and never a member's beneath it — exactly what `seedInputs` seeds, so nothing beneath an optional input structure without a default of its own is listed as a seed, and a model following the brief in order lands on the state the kernel would have seeded; a member's own default stays in its notes, as a fact about the field. What only code can state is here; what a model reads about it is the method's `render_brief` template over this value, so the wording of the brief is edited in the method file like the rest of the prompt. An input is marked delegated when the catalog's own inputs cannot enter it: a file, a date, a list, and a choice that carries an empty option, since the standard puts no floor on a choice while the catalog refuses an empty one — a model told to list the brief's choices exactly would otherwise write a layout the validator refuses. A result is marked delegated when no catalog component can show it: a file, a date, prose, an `unknown`, one of the three native concepts the kind vocabulary cannot name (`native.Date`, `native.Html` and `native.Composite`), and a list of one of those. That last is a list and not a native value, which is why the native predicates refuse it, but its items are values no catalog component reads, so the kernel renders the whole list, one value per line as the result view does, and `payloadToState` hands the hatch the array of whole values it reads. A `native.SearchResult` is not delegated to its arm yet: the brief walks into it as into any structure, so its answer is a text path and each of its sources a delegated document, drawn as a file row rather than as a link, the way a page of an extracted document and a verdict are walked into too; delegating each of them to the kernel's own arm is tracked as separate work. A delegated path ends the walk: the kernel renders it whole, so its members are nobody else's to bind.

A host hands all three to a runner, the method as text and the catalog and the brief as data:

```ts
import { createRequire } from 'node:module';
import { readFileSync } from 'node:fs';
import {
  DESIGNER_BRIEF_CONCEPT,
  DESIGNER_CATALOG_CONCEPT,
  designerCatalog,
  inputBrief,
  seedLine,
} from '@pipelex/mthds-form/generative/headless';

const method = createRequire(import.meta.url).resolve('@pipelex/mthds-form/layout-design.mthds');
const request = {
  mthds_contents: [readFileSync(method, 'utf8')],
  pipe_code: 'generative.design_layout',
  inputs: {
    catalog: { concept: DESIGNER_CATALOG_CONCEPT, content: designerCatalog({ frame: 'composer' }) },
    brief: {
      concept: DESIGNER_BRIEF_CONCEPT,
      content: inputBrief({ pipeRef, description, name }, fields, {
        frame: 'composer',
        style: 'soft',
        result,
      }),
    },
    seed: seedLine(seed),
  },
};
```

The **seed** is optional and travels as the one labelled line `seedLine(seed)` writes, the line the planner's seed procedure was written against: two runs of one brief with different seeds diverge in their composition, and a host that wants a page it can reproduce stores the seed beside the layout.

When the run answers, the producer compiles the JSONL and checks it against the frame it asked for, on the same server, before it stores anything:

```ts
import {
  PROMPT_HASH,
  REPAIR_ATTEMPTS,
  layoutCheckProblems,
  specFromJsonl,
} from '@pipelex/mthds-form/generative/headless';

const problems = layoutCheckProblems(specFromJsonl(jsonl), {
  frame: 'composer',
  descriptor: { inputs: fields },
});
if (problems.length === 0) store({ jsonl, frame: 'composer', promptHash: PROMPT_HASH, seed });
// otherwise repair, at most REPAIR_ATTEMPTS times, as below
```

**The repair pass.** A layout the checks refuse is not lost. The method's second entry, `generative.repair_layout`, takes the same `catalog` and `brief`, the refused JSONL as `page`, and the problems as `problems` — `layoutCheckProblems(spec, check).join('\n')` — and emits the whole page again with those problems fixed and nothing else changed. The loop is the producer's, because the checks are this package's TypeScript and the method cannot run them: check, repair, check again, at most `REPAIR_ATTEMPTS` times, and keep the plain form when the last pass is still refused. The refusals the designer makes are slips of one prop or one child key, which one pass told what it broke fixes; each pass is one model call on the model the method pins, about what the builder stage of a design costs, and its usage comes back with the run like a design's. A layout that needed passes records how many as `repairs`.

A produced layout is stored with its provenance: who produced it, on which model, with which seed, for which frame and style, after how many repair passes, against which prompt hash, from which brief. `SpecFixture` is that record's shape, and `fixtureLabel` renders it — deliberately by **what made the page**, never by a role like "authored" or "generated". A layout the designer method produced also carries the planner's `PagePlan` as `plan`, read from the run's working memory: the intermediate the builder was handed, which is where a page got its shape and the one stage at which two runs of one brief can be compared in words rather than in elements.

### The typed contract

The method's structures are projected into TypeScript rather than mirrored by hand. `src/generated/layout-design/` is that projection: `types.ts` (a zod schema and an inferred type per concept the bundle declares — `Catalog`, `Component`, `Action`, `Brief`, `PathEntry`, `PagePlan`, `PlannedRegion`, and `Text` for the output), `binder.ts` (`parseX` / `serializeX` over them), `codegen.lock` (the engine's fingerprint of the bundle and a content hash per file) and `sources.json` (which method, which target, the pipe's signature, the bundle directory and the SHA-256 of every `.mthds` file under it). It was written by `/pipelex-integrate` through the Pipelex workshop's `ts-zod` target, and it is refreshed the same way after any edit to the bundle. It is **never edited, formatted or linted by hand**: every stamped file carries a hash of its own bytes, so a reformat is drift. `.prettierignore` and `eslint.config.mjs` leave the directory alone for that reason, while `tsc` keeps covering it, because the type check is what catches a call site drifting from its types.

`DesignerCatalog`, `DesignerComponent` and `DesignerAction` are aliases of the generated `Catalog`, `Component` and `Action`, and `DesignerBrief` and `DesignerPathEntry` of the generated `Brief` and `PathEntry`. `designerCatalog()`, `inputBrief` and `resultBrief` build their literals against the shapes the bundle declares, so a field renamed in the method fails the type check on those literals rather than a run. The import is type-only, which is what keeps the generated zod schemas out of the entry: they enter no built chunk, and `make assert-bundle` holds the graph as before. Two hashes now guard two different pairings, and they do not overlap. `PROMPT_HASH` pairs a **captured layout** with the prompt it was produced against; the sidecar's source hash pairs the **generated types** with the bundle they were projected from. `make codegen-check`, part of `make check`, reads the second — every stamped file against the lock, and the method's bytes against the recorded hash — offline, with no engine, no network and no key. Red means the bundle moved and the types did not, and the remedy is `/pipelex-integrate`, never a hand edit of the tree or of `sources.json`.

The worked example of a call is `scripts/pipelex/layout-design.ts`, the fixture harness's own. It loads every `.mthds` file under `methods/` as `mthds_contents` — the directory is the bundle's closure, because a file that imports a sibling needs that sibling submitted with it, and today it holds the one method. A second method added beside it would join this request, and `make codegen-check` goes red naming it as a source the types were not generated from; that red is the signal to give each method its own directory and move the sidecar's `bundle_dir` with it, not to filter by name here. The call sends the catalog and the brief as the contents of two structured inputs, validated by `serializeCatalog` and `serializeBrief` before the run is paid for, runs `design_layout` through `@pipelex/sdk`'s durable start-and-poll, and narrows the answer through `parseText`. It lives under `scripts/` and not under `src/` because the SDK is banned from every entry ([dependency-budget.md](dependency-budget.md)); a host writes the same module against its own client. `PagePlan` is generated too, and the call site reads the planner's intermediate out of the run's working memory through `parsePagePlan` — the hosted results payload carries the working memory beside `main_stuff`, keyed by stuff name — so the plan a fixture records is narrowed by the same binder as the page. The brief as the run laid it out, the `brief_text` the first stage wrote, is read out of the same memory, which is how the specs pass holds the brief on record to the text the model actually saw.

## Where the corpus lives

The layouts in this repo are real: produced by the designer method on the hosted API — the path a product's producer takes — over briefs rendered from real methods, validated on the way in, and committed with their provenance under `src/__stories__/_generated/<case>.specs.ts`. Each hero is designed in each of its frames (`framesOf` in `src/__stories__/heroes.ts`): a whole page with no style, and the moment of a host's app it is — the composer for an input hero, the result page for a result one — once in every app style, with a seed. `make briefs` writes what a producer was handed, one brief a variant (`data/briefs/<pipeRef>.md` for a whole page, `<pipeRef>.<frame>.<style>.md` for a moment); `make fixtures-specs` produces layouts, running the method's repair pass on one the checks refuse exactly as a host's producer does, and keeps one still refused after `REPAIR_ATTEMPTS` passes under `data/briefs/` rather than storing it; `--capture` takes in one another producer wrote, under the same discipline. A layout that is refused however many passes it is given is a fact about the method, and the repair is to the method, never to the fixture. See [storybook.md](storybook.md) § "The passes, and which of them cost anything".

`src/__stories__/__tests__/generative.test.ts` is what those layouts are for: every one of them is asked whether it still compiles from its own JSONL, passes a host's checks for its frame, and was produced against the prompt this entry ships.

### Working on the method

The prompt is the method's text, hashed whole, so any edit to it — a rule reworded, a heading moved, a pipe renamed — moves `PROMPT_HASH` and stales every captured layout at once. Restoring them means re-running the designer on the hosted API, which costs inference budget and returns new pages that want a design review. That is the right price for the edit that ships, and the wrong price between two edits of a prompt, so the loop while the method is being worked on is:

- **`make prompt-hash`** moves the pin to what the method and the catalog hash to now, and writes the one line in `src/generative/prompt-hash.ts`. The pin is what the entry states about the prompt it ships, so it is kept current rather than deferred; it touches no fixture, and `make fixtures-specs` still refuses to run while the pin and the method disagree.
- **`make briefs`** rewrites each hero's brief, whose opening line carries the hash of the prompt it was written beside. It builds the brief as data and lays it out through the method's own `render_brief` stage, run by the local runtime — the sibling `../pipelex` checkout's venv, addressed through `PIPELEX_PYTHON` as `make fixtures` addresses it — so the text on record is the runtime's rendering of the template and nobody's imitation of it, and an edit to the template shows up in the briefs on the next run. A third assertion holds those opening lines to the pin, and it is deliberately **not** one of the two the hatch stands down: a brief is free to regenerate and a captured layout is not, so the loop keeps the briefs current rather than excusing them. Skip this step and `generative.test.ts` goes red under the hatch exactly as it does without one. Free and offline: no model is called.
- **`METHOD_WIP=1 make test`** stands the two stamp assertions down — the fixture's hash against the pin, and the brief's opening line against the fixture's hash — and holds every other one. A captured layout still has to compile, validate against the catalog and fit its descriptor, because a prompt edit staled its provenance and nothing about the page. The skips show in the reporter and the hatch names itself on stderr.

`METHOD_WIP` is local: under `CI` it is ignored and the stamps are held, so a branch cannot merge with a corpus the entry would refuse to render. One `make fixtures-specs` sweep before the pull request opens pays for every edit that came before it. The reasoning is written out in `src/__stories__/__tests__/method-wip.ts`.

**An edit to the method is never a patch release.** The file ships as `./layout-design.mthds`, and a consumer may ship it again as a copy taken from the kernel it resolves; a host sends that copy to its runner and stamps each layout with the `PROMPT_HASH` of the kernel it installed. The two agree only while the method cannot change inside the caret range the consumer declares, and any edit — a reworded rule as much as a new pipe — moves the hash and stales every layout a host has stored. So a release whose diff touches the method, or anything `promptHashSubject` reads, is a minor at minimum; the release skill (`.claude/skills/release/SKILL.md`) says the same.
