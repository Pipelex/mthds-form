# Generative UI over the descriptor

A study, not a feature. Nothing described here ships: the layer lives under `src/__stories__/generative/`, outside both entry trees, and is reachable only through Storybook. It exists to answer one question with evidence rather than opinion — whether a model, given what this package already derives from a method, can lay out a page that a person would rather use than the kernel's own rendering — and, since the first checkpoint answered that with a yes, a sharper one: how far a model can make the input side look like a small web app built for the one job the method does, rather than a schema transcribed into fields. The decisions are recorded in the campaign's plan under `wip/generative-ui/`; this document is the durable description of the layer itself.

## Three artifacts, and which one a model touches

A method reaches a page as three artifacts, and the layer keeps them apart:

- **The descriptor**, `RunField`, which `buildRunFields` and `buildResultField` derive from the wire. It states what every input and every result member IS — its kind, presence, multiplicity, label, constraints — and the package's first rule is that nothing downstream re-derives that.
- **The state**, two JSON trees json-render's store holds: `/inputs`, one member per input, written by the controls and read by the run; and `/result`, loaded from a run's payload before the page renders, read-only. The host owns both. On the result side `payloadToState` turns the wire into the tree by the kind the descriptor states — a date becomes its ISO string, a plural result sheds its `{items}` envelope, a document or an image stays as the serializer wrote it — and on the input side `seedInputs` plants the authored defaults and nothing else, because a seeded empty string would count as filled.
- **The spec**, a json-render `Spec`: a tree of elements over a fixed catalog, every value bound to a state path. This is the only artifact a model produces, and it is a per-method artifact — it carries no descriptor and no data, only paths — so it is produced at design time, once per method version, and rendered at run time over whatever state a run yields.

Rule 1 restated for a model: **the brief is the only source of paths; bind every value to one of them, exactly as written, and inline nothing the state carries.** A spec that restates a field's kind, copies a value from the example run, or invents a unit the state does not carry has broken the seam the package is built around, and the corpus test treats each of those as a failure rather than a style choice.

## The catalog, and the two escape hatches

The vocabulary the model lays out with is `catalog.ts`, in two layers. From json-render's shadcn components, the subset a page needs and nothing that cannot bind — `Card`, `Stack`, `Grid`, `Separator`, `Collapsible`, `Heading`, `Text`, `Badge`, `Alert`, `Progress`, `Avatar`, `Input`, `Textarea`, `Select`, `Radio`, `Checkbox`, `Switch`, `Button` — with `className` removed from every prop schema (colour, spacing and type come from the components as they are, themed through the same tokens as the kernel's controls) and `Card`'s width props removed too, because shadcn's "lg" card is narrower than its page. Then the layer's own: the two escape hatches; `DataTable` and `Metric`, the bound equivalents of what a model most wants to inline; and the vocabulary of an app rather than a form — `Tabs` whose panels follow the active tab (the reason shadcn's is not picked), `Steps` for a journey with its own Back and Next, `Split` for a rail beside the work, `Segmented` for a choice as pills, `NumberInput` that writes a number where shadcn's `Input type="number"` writes text, and `Icon`, a closed list of lucide names, to give a section a face. The panelled containers keep their state to themselves: the active tab and the current step are the component's own, never `/state`, so a spec never carries UI state and a hidden step hides an input from the eye and never from the run. Two things are deliberately absent: `Slider`, because the standard states no bounds on a number and a slider with invented bounds narrows the input; and `Image`, because the layer has no image source that is not the state.

`MthdsField` and `MthdsResult` are what keeps the layer honest. Each takes a `path` and nothing else, resolves it against the descriptor the host already holds (`DescriptorProvider`, `paths.ts`), and hands the `RunField` it finds to the kernel's own `FieldRenderer` or `ResultField`. Every kind the catalog cannot show properly — a file, a date, a document, prose, a list of structures on the input side — is delegated this way, and so is any structure the model would rather not lay out. Delegating a subtree whole is a valid outcome, not a failure; the design says so, and the Company hero exists to see whether a model takes the offer gracefully. Inside a `repeat`, a hatch's path is the item's field name relative to the item — `"teams"` inside a card repeated over the divisions — and the hatch resolves it against the repeat scope json-render provides, which is what lets a model lay out one level and delegate the next for every item at once. A path is always a literal string: the validator refuses an expression there, because the layer resolves the path and an `$item` expression would have been resolved to a value before the hatch saw it.

The `path` form is a deliberate departure from the first design, which had the spec carry the descriptor verbatim. A spec that carries a `RunField` restates what a field is, and a model asked to copy a JSON subtree is a model given a way to get it subtly wrong; a path is the stricter reading of rule 1, and it is what makes a spec descriptor-free.

## The prompt is ours

json-render's stock schema ships a prompt template whose posture is to invent state: an "initial state" section demanding `/state` patches for every bound path, and default rules asking for sample data. That is the opposite of this layer's premise, so `schema.ts` defines the same spec shape and the same built-in actions with its own default rules and its own template, composed from the same section vocabulary so a model's priors still apply. `rules.ts` adds the rules a spec is refused for breaking — the brief is the only source of paths, no `/state` on a result page, delegate what is marked, one Button that fires the run, one panel per tab or step, option lists exactly the brief's choices, no `className`, heading levels increase by one — and the corpus test asserts the words the stock template would have contributed never reach the prompt.

What the page must FEEL like is a section of its own, `direction.ts`, rendered into the prompt as `DESIGN DIRECTION`: a small web app, not a form; start from the feeling and name the page after the job; stage the inputs in the order a person thinks; prefer the control that feels like an app; use structure rather than decoration; restraint reads premium; copy a person would say; bold is allowed. It follows the method documented in the workspace's design research — an ambitious, specific brief rather than a plain one, and restraint over decoration — and, because it is part of `catalogPrompt()`, the hash covers it: a change of ambition invalidates a fixture exactly as a change of vocabulary does. The same file carries the `CREATIVE SEED` procedure, the answer to a model's inability to be random on its own: when a seed string follows the brief, the model derives its composition, density and tone from it and never shows it, so two runs of the same brief diverge. The seed is an input, not part of the prompt — the specs pass mints one with `SEED=1` and a subagent is handed one in its message — and the fixture records it.

`catalogPrompt()` renders the whole thing, and `promptHashOf` stamps it. The hash is what ties a spec to the prompt it was produced against: every captured and every authored spec carries one, the corpus test compares it with the current prompt, and a catalog change is therefore a failing test rather than a stale page. A stale hash means regenerate the captured spec and re-read the authored one against the new prompt.

## The brief

What a model is given, besides the prompt, is a brief per hero (`brief.ts`), rendered from the committed descriptors and payloads by `make briefs` into `wip/generative-ui/briefs/`. An input brief lists every path under `/inputs` with its kind, presence, whether it gates the run, its label and constraints, marks the paths to delegate, names the defaults to seed and says which inputs the run waits for. A result brief lists the paths under `/result` the same way, with a list's items described by their members' paths relative to one item, and shows the state of one real run as JSON so the model judges magnitudes without seeing the wire. The catalog prompt follows in the same file with its hash, so the brief is the complete record of what both the model and a human author were handed.

## Producers, and the names a page gets

Every hero renders from the very same fixture, so the only difference on screen is the layout, and every page is titled with what made it — never with a role. The first two stories of a hero are fixed: the package's own form or result view (the faithful transcription, what a host gets with no layer at all) and the deterministic projection, `projectInputSpec` / `projectResultSpec` over the fields (the floor: one element per member in descriptor order, no inference). Every other story is one captured spec, and its provenance is the whole of its title:

| Producer                                | What it is                                                                                                                                                             |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pipelex-method` on a named model       | The designer method, `data/generative/ui-designer.mthds`, run through the real CLI by `make fixtures-specs`, on the model `MODEL=` names                               |
| `claude-code-subagent` on a named model | A Claude Code subagent in a fresh context, handed the prompt and the brief and nothing else, whose JSONL is taken in by the `--capture` command                        |
| `claude-code-session` on a named model  | The Claude Code session working in this repo, writing the spec by hand in TypeScript with the whole codebase in context, typed per component so a bad prop fails `tsc` |

A fixture also records the creative seed when one was handed over, and the critic model and rounds when a producer ran a fresh-context critic loop over screenshots; `fixtureId` and `fixtureLabel` in `spec-fixture.ts` turn the record into the story's id (`pipelex-method--gpt-5.5--seeded`) and its title (`Pipelex method · gpt-5.5 · with a seed`). The reading follows from the bounds as before — a model's page close to the hand-written one clears the model, the hand-written one dull too indicts the catalog, the projection nearly as good as either says the layer has not earned its place — with the producers now named, so the comparison can also say which model, which harness and which prompt variant did what.

`hero-page.tsx` is the harness the generative stories share: it derives the descriptor through the kernel's own lookups, loads the state, owns the store and hands the page a spec, and on the input side shows the receipt a host never would — the `/inputs` tree as the run would receive it and the readiness the kernel computes from it — which is what the play functions assert against. `Streamed` replays a captured spec line by line through json-render's stream compiler, so the progressive fill a host would see from a live generation is visible without one.

## Design time and run time

Generation is a design-time act: the designer method (`data/generative/ui-designer.mthds`, one `PipeLLM`) takes the catalog prompt, a brief and an optional seed and returns JSONL. `make fixtures-specs` runs it through the real CLI for each hero — `MODEL=` names the model, `TEMPERATURE=` overrides the pin's temperature for a model that fixes its own, `SEED=1` mints a seed per hero — compiles the text, validates it against the catalog with the layer's own validator (`validate.ts`, which checks every prop per component, is expression-aware where json-render's own check degrades to "any record" once a catalog has more than one component, and checks that a `Tabs` or `Steps` has one child per panel), and stores the fixture in `src/__stories__/_generated/<case>.specs.ts` beside the case's other fixtures, replacing the one with the same producer, model and seededness. A spec another producer wrote enters by the same door: the script's `--capture` command takes a JSONL file with `--pipe`, `--producer`, `--model` and optionally `--seed` and `--critic`, validates it exactly as the method's text is validated, and stores it with the current prompt hash. A rejected spec is kept beside the brief and the command fails; the repair is to the prompt, the method or the producer's procedure, never to the fixture. Both passes cost inference and need credentials, which is why neither is implied by `make fixtures` or `make fixtures-runs`.

Rendering is a run-time act that needs no model: `GenerativePage` takes a spec, a store and the descriptor scope, and json-render's renderer does the rest. That split — one spec per method version, rendered over every run — is the shape any adoption of this layer would take, and it is why the spec is deliberately descriptor-free.

## The brand as data

The prototype's question — what the layer looks like when a page is built as a **product page in a real brand** — got its first answer as a spike with a hand-written stylesheet, and the redirect that followed is the rule this section is built on: **the brand is data.** A brand is two JSON files a producer writes, `tokens.json` (the palette, the radius and the typefaces, in the DTCG token format) and `brand.json` (the name, the site, a logo for each canvas, the web font to load), validated against a contract and compiled into a scoped stylesheet by a build. Nothing on the page is painted from anything else, so anything the tokens cannot state is not on the page — the first prototype's orbs and canvas gradient went for exactly that reason. The code is under `src/__stories__/generative/brand/`, the data under `data/brands/<brand>/<producer>/`, and one story per producer renders the same page from each producer's data, titled by what produced it.

**The contract** is the package's own theming contract, stated as data: `contract.ts` lists which token sets which custom property and what that property paints — the shadcn colour tokens, `--radius`, `--font-sans` and `--font-mono` — and the node test asserts the table and `theme.css` name the same variables. `make briefs` renders it as `wip/generative-ui/briefs/brand-contract.md`, the document a producer is given, with the file rules, the manifest's JSON Schema and a skeleton of each file; the hash of that text is the `contractHash` every brand's provenance carries, so a contract change invalidates every brand written against the old one, loudly, exactly as a prompt change invalidates a spec.

**The pipeline** is ours once and Terrazzo after: `tokens-schema.ts` checks the contract's own rules first — exactly its tokens, object colours in sRGB, aliases only to contract tokens and never in a cycle, a description on every token, `dark` the only mode and stated on every colour object (an alias may carry its light value alone and then stands for both modes, following its target — the pipeline fills its dark mode in with the same alias before Terrazzo, so the stylesheet still sets every variable in both of its blocks), and the two contrast pairs (foreground and muted-foreground on the canvas, WCAG AA) in both modes — because the DTCG parser is looser than the contract in every direction that matters: it accepts any token, turns an unparseable string colour into black, passes a hex with no components to a build that crashes on it, and checks contrast on the light value only. `terrazzo.ts` then runs the parser, its lint and its CSS plugin on a file it can only accept, collecting every message rather than throwing on the first, and emits the contract scoped to one class: `.brand-<brand>-<producer> { --background: …; --card: var(--background); … }` and a `.dark .brand-<…>` block for the dark values. Its `duplicate-values` rule is a warning recorded on the fixture, never a failure, because it counts an alias as a duplicate and a palette legitimately repeats white. `make brands` runs the pipeline over every brand directory and writes `src/__stories__/_generated/brands/`: one stylesheet per brand and producer, an `index.css` importing each, and `brands.ts` carrying each brand's provenance, manifest, tokens, scope and stylesheet — all or nothing, with the problems printed in the contract's words. The node test `brands.test.ts` rebuilds every brand from its data and fails on a committed stylesheet that is not what the data produces, and carries the validator's own cases, each a way a file can be wrong that Terrazzo would let through.

**The page** is the prototype's, re-based on the tokens alone. `brand-catalog.ts` still extends the layer's catalog with the vocabulary of a product page — `AppBar`, `Hero`, `Workspace`, `Section`, `Rail`, `SummaryRow`, `Cta`, `Footer` — and names no brand: the logo is whichever the manifest carries, the accent whichever the tokens set. `brand-registry.tsx` paints them with no literal colour, radius or typeface: a hairline is `border-border`, the rail's panel is `bg-card` on `border-border`, the corners are `--radius` and its multiples, and the call to action's glow is the accent composed with `color-mix()` rather than a shadow token, because nothing consumes one. The logo is the manifest's pair, one shown on each canvas through the `dark:` variant, both with the brand's name as their accessible name. `brand-page.tsx` puts the scope class on the root beside `font-sans` — which makes Tailwind emit `--font-sans`, so the scoped token overrides the typeface — and a `BrandProvider` hands the manifest down and appends the Google Fonts link a host would put in its head, once per family; the Storybook carries no font any story did not ask for. Under the page, folded away, the `/inputs` tree the run receives and the stylesheet the brand was painted from, titled by its provenance. `pipelex-trip.spec.ts` is unchanged: the spec is the page's layout and copy, and it is the same in every brand story.

**The first brand** is the session's own, `data/brands/pipelex/claude-code-session--claude-fable-5-1/`, written by hand from pipelex.com — the site is dark by default, so the dark values are its own and the light ones are derived — and it renders the trip planner in both themes with no hand-written CSS anywhere: the right logo per canvas, Inter, the teal accent and its glow, the site's glass card on the dark canvas. The story `Generative/Brand/Pipelex · trip planner` shows both themes side by side, because a brand is two palettes and the pair view is how a wrongly derived mode is seen; its play asserts the manifest reaches the page (one logo per pane), the tokens reach the paint (the call to action's computed colour is the token's, the page is set in the token's typeface) and the kernel still owns the inputs. The rules that count landmarks per document are off for the brand stories only, since the pair view renders a page with a banner, a rail and a contentinfo twice on one document.

**The producer** is a Pipelex method and a script around it, and the split between them is this section's rule applied to the producer itself: what a site declares is a matter of fact, and a script reads facts exactly, every time, for nothing; what a model is for is the judgment the facts do not carry. `scripts/extract-site-facts.mjs` fetches a page and its stylesheets and records, as data, how the site declares its colour scheme (the `html` class, the `body` data attributes, its `color-scheme` declarations), every colour custom property with each of its declarations and the selector it is set under, the colour utilities the markup uses most with the colour each resolves to, the colour literals by frequency, the typefaces and font links, the radii, and the images that could be a logo. One fact is computed rather than copied: for each custom property, `asServed` is the declaration that wins for the page as it is served — by source order among the declarations whose selectors match the root in the scheme the page starts in — which is what decides between a framework's `:root` default and the site's own override loaded after it, and what a model handed a long list of declarations of one name got wrong before the field existed. The method, `brand.tokens_from_site` in `data/generative/brand-designer.mthds`, takes the contract brief and the facts and answers with one JSON object carrying both files; its judgment is the mapping — which colour is the accent and which the canvas, what the other mode of a one-mode site is, which image is the logo and which canvas it was drawn for. What a site does not show, no reading can supply, so the person who owns it may state it beside the URL — `ACCENT=#rrggbb`, with `ACCENT_DARK=#rrggbb` when the dark canvas needs another, `LOGO_ON_LIGHT=<url>`, `LOGO_ON_DARK=<url>` — for the accent of a site with no button and the logo for a canvas the site draws none for. A stated fact enters the facts as `stated`, the accent per mode, ahead of every reading; the method is told it outranks them; the build checks the brand honours it, `color.primary` resolving to the stated accent in each mode it is stated for and the manifest carrying the stated logo for its canvas; and the provenance records it, so a brand from such a site is still a reading of something a person said. `make brand-from-site BRAND=<slug> URL=<url>` runs the loop end to end and timed: extract, generate through the real CLI, validate with `assembleBrand` exactly as `make brands` validates a committed brand, hand the problems back in the contract's words for a bounded number of repair rounds, write `data/brands/<brand>/<producer>/` with the provenance (producer, model, date, the brief and its hash, the facts file, the rounds) and `rounds.json` when a repair ran, and rebuild. Past the bound the last answer is kept beside the brief as a rejected file and the command fails; the repair is to the method, the extractor or the contract, never a hand edit of the data.

**Two sites**, so that the mapping is not tuned to one page; each brand's facts sit beside its producer directories as `data/brands/<brand>/site-facts.json`. From pipelex.com, a dark-first site with a teal accent, the method's brand matches the session's hand-written one where the facts are explicit and improves on it where they are not: the light mode, which the site never shows, has an off-white canvas, a translucent grey card and inputs that stand off it, where the hand-written brand had made the card the canvas. From mthds.ai, a light-first documentation site set in Roboto with a near-square radius and a monochrome palette, everything the facts state came out right and stable across runs — the canvas, the ink, the hairline, the surfaces, the typefaces, the radius, the logo — and its story is `Generative/Brand/MTHDS · trip planner`. What that site never shows is a button, so its accent was a decision rather than a reading, and the method answered it differently on each run — a framework palette default the site overrides, then the site's own near-white primary surface — until the accent was stated beside the URL — per mode, because that site's header ink is near-black on its light canvas and near-white on its dark one, and one near-black accent stated for both modes vanished into the dark canvas the first time a page was read in it. Both sites reference one logo file, drawn for one canvas, and each publishes the other variant without linking it from the page, so the missing one is stated too: the white mark for mthds.ai's dark canvas, the black mark for pipelex.com's light one. With those stated, both brands validated on the first call in under forty seconds. Before the alias rule, three of five runs needed one repair round, every one for an alias written without its dark value; that is the fault the rule removed.

What the first prototype established still holds, and is now a property of the data rather than of a stylesheet: the tokens re-skin the kernel's controls completely, and a date, a list and a dropzone sit on the brand's card with no change to `src/react/`. The two control findings it surfaced — a list's empty placeholder stacking over its _Add item_ row, the date control's mono face — are recorded in the study's plan for the controls themselves, where they belong. Nothing here ships; `make assert-bundle` proves it.

## The join: the method's layout under the method's tokens

The brand section answers what a page looks like in a brand; the study's question is whether the whole chain gets there with no coding agent in it. Two things had been shown separately — the designer method laying out a page from a brief, and the brand method writing a brand from a site — and the page that read as a product page carried a layout a Claude Code subagent had written by hand. The join is the method's own layout under the method's own tokens, and it is built on two seams the layer already had.

**Any layout renders in any brand.** `BrandPage` takes any spec and `brandRegistry` extends the layer's registry, so a spec captured against the layer's own catalog renders under a brand's tokens unchanged. `brandStories` has two shapes for that: `of(producerId)` is the reference, the hand-written brand spec under one producer's tokens; `join(producerId, layoutId)` is a captured layout under one producer's tokens, titled by what produced each half — `layout Pipelex method · claude-4.8-opus · tokens Pipelex method · claude-4.8-opus`. A base-catalog layout brings no chrome and no container, since that catalog has no notion of a page's width, so `BrandPage` takes `contained` and a story sets it for such a layout; the play then proves the tokens reach the paint (the run button's computed colour is the token's accent, the page is set in the token's typeface) and the kernel owns the inputs (a typed budget reaches its path, the readiness on the receipt is the kernel's own). What that showed is recorded in the campaign plan: the tokens re-skin a method-made wizard completely, and it still reads as a form, because the weight of a page — a bar with a logo, a headline, flat sections, a rail, a footer — is vocabulary the base catalog does not have.

**The designer method takes any catalog.** The method was written coupled to none: the catalog's rules arrive as an input. `brandCatalogPrompt()` renders the brand catalog's prompt with the layer's own template — the same design direction, the same seed procedure, the wider vocabulary — and `BRAND_RULES` (`brand-rules.ts`): every rule of the layer's prompt with one restated, the Button rule for the Cta in its place, and the grammar of a product page appended — the root a Stack of AppBar, Workspace and Footer in that order; the Workspace of the work and the Rail; the work opening with the one Hero, whose headline is the page's only h1, then a numbered Section per concern, flat, never a Card; every input inside a Section; the Rail made of SummaryRows bound to input paths and ending with the one Cta firing `validateForm` then `run`. The grammar is stated as rules and not guarded by the validator, so that a run measures the prompt rather than the guard. The prompt has its own hash, `currentBrandPromptHash()`, and the brief the method is handed names the Cta as what runs the page (`callToAction` on the brief subject), written by `make briefs` as `wip/generative-ui/briefs/<pipeRef>.brand.md` beside the base one, which does not move. The `Section` renderer spaces the children it is handed, since the rules put a concern's inputs flat inside it and the method writes them so; the hand-written spec had wrapped its own in a `Stack`, which no rule asks for.

**The pass takes a catalog.** `make fixtures-specs CATALOG=brand ONLY=<pipe code> MODEL=<id>` hands the method the brand prompt, validates what came back against the brand catalog — `validateAgainstCatalog(spec, catalog)` runs the same checks over whichever catalog it is given, the layer's own by default — stamps the brand hash, records `catalog: 'brand'` on the fixture, and writes `src/__stories__/_generated/<case>.brand.specs.ts`, so the base module, its corpus test and its stories are untouched; a rejected answer is kept as `<pipeRef>.brand.<id>.rejected.jsonl` and the pass fails. `fixtureId` ends in `--brand` and `fixtureLabel` says `brand catalog`, so a story titled by its fixture says which vocabulary the page was written in. The corpus test has a describe over the brand-catalog fixtures: each validates against the brand catalog and not against the layer's, was produced against the current brand prompt, round-trips its JSONL, carries the grammar (bar first, footer last, one each of AppBar, Hero, Workspace and Rail, one Cta and no Button, no Heading at h1), delegates and binds only to paths the descriptor has, and writes the budget as a number.

**What a run of it produced,** for each model tried, is a page in the brand's grammar on the first call, with zero repair rounds, rendered under each method-made brand as one story per model in both brand story files with the brand play in full. The reading — whether it reads as a product page, judged on the shots beside the hand-written reference — is the campaign plan's, under its Checkpoint 9.

## What ships, and what would come next

Nothing ships. The json-render packages, `zod` and `radix-ui` (for the layer's own `Tabs`) are devDependencies, importable only from the story tree, and `make assert-bundle` would fail the moment one reached a shipped chunk. What is committed is the layer, the designer method, the briefs, every captured and hand-written spec with its provenance, and the corpus test that keeps them honest.

If the study's checkpoint decides the layer earns its place, the recorded follow-ups are a `./generative` entry or a sibling package, hosted generation and caching of the spec per method version, the agent skill for the authored path, and a zod mirror of `RunField` so a host can validate a spec without this package's help. Each is out of scope here and named in the campaign plan so that none is absorbed silently.
