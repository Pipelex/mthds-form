# Wording a form for its reader

A form built from a method speaks two vocabularies. The controls' own copy — "Add item", "optional", "Drop a file or click to browse" — belongs to this package, and this page is how a host puts it in its reader's language. Everything else a form shows about a method — its field labels, helper lines and enum choices — comes from the method itself, from its names and descriptions, and never from the host: a method meant to read in French is written with French descriptions.

## The controls' copy: `FieldStrings`

Every string a control renders comes through `FieldStrings`, with complete English defaults (`DEFAULT_FIELD_STRINGS`). A host mounts `FieldStringsProvider` above the form with a partial or complete set, merged over the defaults. Count-bearing messages are functions rather than templates, so each locale applies its own plural rules.

`FR_FIELD_STRINGS` is a complete French set, exported from `./react` for a host that has no catalogue of its own to bridge. It applies French plural rules (zero and one take the singular: `0 élément`, `1 élément`, `2 éléments`), writes a file size as `36 ko` or `1,4 Mo`, and puts a no-break space before a colon. Plurals and sizes come from the platform's `Intl` (`PluralRules('fr')`, `NumberFormat('fr-FR', { style: 'unit' })`) rather than hand-written rules. Locale packs live in `src/react/locales/`, one file per language (`fr.ts`); a new language is a new file there, exported from `./react` the same way. It is typed as a whole `FieldStrings`, so a key added to the contract fails the build until it is translated. A host that wants a different word for one key spreads it: `{ ...FR_FIELD_STRINGS, addItem: 'Ajouter une ligne' }`.

`describeValidationError` takes the host's own `Translate` over its `ValidationMessageKey`s. The package ships no message table for those keys in any language, English included, because they are namespaced in the host's catalogue (`inputPanel.*`); a French host adds the six keys to its own catalogue.

`MethodForm` takes the same two props, `locale` and `strings`, and mounts the provider around its fields when either is given ([method-form.md](method-form.md)). Its marks are keys like any other: `requiredField`, `incompleteField` and `uploadFailed`.

## Choosing the language per user

A host serving several languages passes the user's locale and lets the package pick the pack: `<FieldStringsProvider locale={user.locale}>`. `fieldStringsFor(locale)` reads the code as BCP 47 and keys on its primary language subtag, so `fr`, `fr-FR` and `fr_CA` all give French, and a missing or unknown locale gives English. `strings` still overrides single keys on top of the chosen pack: `<FieldStringsProvider locale="fr" strings={{ addItem: 'Ajouter une ligne' }}>`. The shipped packs are listed in `SUPPORTED_LOCALES` and `FIELD_STRINGS_BY_LOCALE`; English lives in `src/react/locales/en.ts` and stays exported as `DEFAULT_FIELD_STRINGS`.

To add a language, add `src/react/locales/<code>.ts` typed as a whole `FieldStrings` (the build fails until every key is translated), take plurals and sizes from `Intl` for that code, add it to `FIELD_STRINGS_BY_LOCALE` in `src/react/locales/index.ts`, and export it from `./react`.
