# The whole form: `useMethodForm` and `MethodForm`

`FieldRenderer` renders one input. Every host that renders a method's whole input form used to write the same hundred lines around it: derive the fields, seed the method's defaults, hold the values, upload a dropped file and write it back at its path, track which uploads are in flight and which failed, fold the empty optional inputs behind a disclosure that also opens and closes the optional structures, mark the required inputs once the person has tried to run, and turn the values into the inputs a run takes. Each copy got some of it slightly differently. The `./react` entry now ships that as two pieces:

- **`useMethodForm(options)`** holds the state of one method's form and returns a controller: the fields, the values, the run inputs, the readiness and whether the run may start.
- **`<MethodForm form={controller} />`** renders every input for that controller, and nothing else.

They are two pieces so that the consumer keeps what is its own. The hook is called wherever the run button lives (often a page, with the form in one panel and the button on a seam between panels), and the component is mounted where the fields go. Neither carries a panel, a heading, a run button, a run history or a `<form>` element: a host wraps the fields in whatever it has.

```tsx
import { getPipeInputForm, getPipeIOContract } from '@pipelex/mthds-form';
import { MethodForm, useMethodForm } from '@pipelex/mthds-form/react';

const contract = getPipeIOContract(method.pipe_io_contracts, method.domain, pipeCode);
const descriptor = getPipeInputForm(method.input_form, method.domain, pipeCode);

function RunPanel() {
  const form = useMethodForm({ descriptor, contract, uploadFile });
  return (
    <form
      onSubmit={(event) => {
        event.preventDefault();
        if (form.attempt()) startRun(form.inputs);
      }}
    >
      <MethodForm form={form} locale="fr" presentation="app" disabled={running} />
      <button type="submit">Run</button>
    </form>
  );
}
```

## What the hook takes

| Option                   | What it is                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `descriptor`, `contract` | The pipe's input-form descriptor and its `pipe_io_contracts` entry, the two wire artifacts `buildRunFields` takes.                                                                                                                                                                                                                                                                                                     |
| `prepareFields`          | A transform over the derived fields, applied before anything else reads them: narrowing a file slot with `narrowFileFormats`, dropping a child the host never sends. It must be stable (module-level or memoized), because the fields are re-derived when it changes.                                                                                                                                                  |
| `order`                  | Input names to show first, in that order. The rest keep their descriptor order after them, and a name no input has is ignored.                                                                                                                                                                                                                                                                                         |
| `initialValues`          | What the form holds until its first edit. Absent, the method's seed (`seedInputs`). A function receives the seed and returns the values, for something the method cannot know, such as today's date.                                                                                                                                                                                                                   |
| `uploadFile`             | `(file, { id, path }) => Promise<string \| { url, filename? }>`: stores a file and resolves to its URL. Its presence is the capability; without it every file field is link-only, as [upload-seam.md](upload-seam.md) describes. The context names the id the file was dropped at, and the form writes the result wherever that row stands when the upload lands.                                                      |
| `fileSource`             | The host's stored files, listed a page at a time (`FilePickerSource`), with an optional `renderGlyph` that draws each row's glyph in the host's own look. Its presence is the capability: every empty file field then offers "Choose from your team's files", and a list of files offers it for several at once. See [sources.md](sources.md).                                                                         |
| `exampleSource`          | The method's saved examples (`ExamplePickerSource`), with an optional open, which hands a row's example to the host's own surface with a `fill` for it, an optional rename and delete, and an optional `renderDetail` that draws a line under each row's name in the host's own words. Its presence is the capability: `MethodForm` then offers "Fill with an example" above the fields. See [sources.md](sources.md). |

`initialValues` is read on every render until the first edit, and from the first edit the form owns its values. That is what lets a statically prerendered page seed today's date from the browser: the server render has no date, hydration supplies one, and the form shows the seed for that day until the person types. A restored run is the other common case: pass its values (from `runValuesFromStore`) and the form opens on them.

A different method is a different form. When the descriptor changes, remount with a new `key`: values belong to the inputs they were typed for.

## What the hook gives back

| Field                         | What it is                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fields`                      | The `RunField[]` the form renders, derived, prepared and ordered.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `values`                      | The current values, in the controls' own shape.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `inputs`                      | The values as a run takes them, from `apiInputsFromRunValues`: each input as `{ concept, content }`, an unfilled optional input left out, an empty plural input sent as `[]`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `readiness`                   | `computeReadiness` over the values: `{ total, ready, missing }`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `uploading`                   | Whether an upload is still in flight, or a file is being made for one (`preparingIds`). |
| `ready`                       | Whether the run may start: every gating input filled, no upload in flight and no file being made. |
| `preparingIds`                | The ids of the file fields making a file they have not handed to `dropFile` yet: photos taken on the camera being read into pages, or pages being bound into a PDF ([camera.md](camera.md)). They count as uploads in flight. They follow the rows `removeItem` and `moveItem` move, a removed row's id is dropped, and a reset forgets them all. |
| `attempted`                   | Whether `attempt()` has been called since the last reset.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `touched`                     | Whether the form holds work of the person's own: values that would send a different run from the ones it was last given (its initial values as they stood at the person's first edit, or the last `reset`), or a file still arriving or being made. Initial values the host changes after that first edit move no baseline, so an edit stays the person's own even when the new initial values happen to match it. A value typed and erased again does not count. "Fill with an example" asks before replacing a touched form. Since `setValues` is how the person's edits arrive, a value a host writes through it counts as the person's too: a host that prefills the form gives the values through `initialValues` or `reset`, which are what the form was given.                                            |
| `setValues(next \| updater)`  | Replaces the values, or updates them from the previous ones. A write that changes the file at a field whose upload failed ends that failure. It is read by position: a write that moves a list's rows reads as one that replaced them, since the values cannot say which it was.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `removeItem(listId, index)`   | Removes the row at `index` of the list at `listId`, the list's dotted value path (`attachments`, `candidates.1.letters`), and moves with every later row what the form keeps by its id: a failed upload's mark, an upload in flight and the file it was dropped over. What it kept for the removed row goes with it. `MethodForm` hands it to its lists as `onRemoveItem`, so a list's remove button uses it; a host rendering its own fields passes it the same way. A call naming no row changes nothing.                                                                                                                                                                                                                                                                                        |
| `moveItem(listId, from, to)`  | Moves the row at `from` to `to`, the rows between shifting by one, and carries what the form keeps by each moved row's id, as `removeItem` does. A host reordering a list uses it rather than `setValues`. A call naming no row changes nothing.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `rowMoves`                    | Every move `removeItem` and `moveItem` have made since the last reset, oldest first (`RowMove`). `MethodForm` hands it to its lists as `FieldEnv.rowMoves`, and a list replays it on its rows' identities, so a row keeps its controls whether its own remove button or the host moved it; a host rendering its own fields passes it beside `removeItem` ([upload-seam.md](upload-seam.md#a-row-keeps-its-controls-whoever-moves-it)).                                                                                                                                                                                                                                                                                                                                                             |
| `reset(values?)`              | Goes back to `values`, or to the initial values, and forgets the attempt, the failed uploads and any upload still in flight, whose result is then dropped.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `resets`                      | How many times `reset` has run. `MethodForm` keys its fields by it, so a reset remounts them and nothing a control kept for the values it replaced survives (the preview of a file still arriving, a refused drop, an open preview). A host rendering its own fields keys them the same way.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `attempt()`                   | The run button's press: it marks the attempt and returns `ready`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `dropFile(id, file)`          | The upload seam `MethodForm` hands its file fields as `onDropFile`, absent without `uploadFile`. It returns the upload, which resolves to the file it wrote at the id's path, or at its row's new id when `removeItem` or `moveItem` moved the row meanwhile, and rejects when it wrote nothing (the upload failed, or a newer drop at the same id, a reset or the removal of its row replaced it), and a file field matches that answer to its value to keep the dropped file's preview. A host rendering its own fields passes it to them unchanged, beside `uploadingIds`, `failedUploadIds`, `removeItem` and `rowMoves`; ignoring the promise is safe, since the form handles its rejection itself ([upload-seam.md](upload-seam.md#the-local-preview-belongs-to-the-value-it-was-made-for)). |
| `preparingFile(id)`           | The seam `MethodForm` hands its file fields as `FieldEnv.onPreparingFile`: a field calls it when it starts making a file and calls the release it returns once it has handed the file over or given up ([upload-seam.md](upload-seam.md#a-file-being-made-is-an-upload-in-flight)). Each report is kept by its own token at its row's id, follows `removeItem` and `moveItem` as an upload in flight does, and goes with a removed row or a reset, after which its release changes nothing. A host rendering its own fields passes it beside `dropFile`. |
| `fileSource`, `exampleSource` | The sources the hook was given, which `MethodForm` hands its fields and mounts above them.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

`ready` is the browser half of the run gate ([run-gate.md](run-gate.md)): readiness, the same predicates the server gate re-applies, plus the uploads, which only a browser has. The schema half, `gateRunInputs`, stays where it belongs, on the server: it carries ajv, which the `./react` entry never ships ([dependency-budget.md](dependency-budget.md)). A host that wants the schema verdict in the browser anyway calls it from the core entry over `rjsfDataFromRunValues(form.values, form.fields)`, and can show what it refuses through `MethodForm`'s `errors`.

A run button need not be greyed out until `ready`. A pressed button with something still missing can say what is missing: `attempt()` returns `false`, and every gating input still empty shows its mark where the person is already looking.

## What the component renders

`MethodForm` renders each input through `FieldRenderer`, with the input's name as its id, so a file's upload id is its value path, as the upload seam requires.

- **The top-level optional disclosure.** The empty optional inputs fold behind "+ N optional inputs", exactly as the empty optional fields of a structure fold behind "+ N optional fields", and closed optional structures fold with them. Expanding opens every closed optional structure with its seed; collapsing closes every one, so it leaves the run inputs ([architecture.md](architecture.md#optional-structures)). `foldOptional={false}` shows every input from the start; a closed optional structure still folds, because it has no control of its own and the disclosure is what opens it.
- **A form its host has framed.** A structure among the inputs draws its own hairline card by default, which is what says where it ends on a bare page. A host that draws the form inside a panel of its own passes `framed`, and each such structure is then a section instead: its name a heading over its fields, with a hairline across the form between it and any input or disclosure beside it, and no card inside the host's panel. When the run gate refuses such a structure, the section has no card to turn red, so it draws a red bar down its side, 4 pixels off the form as a field's own error outline stands off its field, and sets its message beside its heading rather than under its last field. No field moves sideways, and the fields move down by a line only when the message wraps under a long name on a narrow row. The bar asks the host's panel for 7 pixels of unclipped room beside the form; a panel that clips closer than that loses the bar, while the message at the heading still shows ([architecture.md](architecture.md)).
- **The marks.** After `attempt()`, a gating input still empty is marked `requiredField` ("Required"), and an optional input that was started but is incomplete is marked `incompleteField`: a started structure owes its concept every required field. A structure the run gate refuses also marks each field inside it that the gate refuses, at every depth and by the rule the gate reads (`fieldFilled`): an empty required field `requiredField`, and a started optional structure that is not complete `incompleteField`, which in turn marks its own. So the person sees which of a structure's fields are empty rather than reading every one, while an optional structure left closed, and the rows of a list, mark nothing. A message in `errors`, keyed by input name, replaces either mark on the input. It marks none of a structure's fields, since it speaks of the structure; the fields the form's own gate refuses keep their marks beside it.
- **The host's sources.** With a file source, each empty file field offers the team's files under its own controls, and a chosen file is written as an upload's result is. With an example source, "Fill with an example" sits above the fields; filling is a `reset` to the example's values, asked about first when the form is `touched`, and never starts a run ([sources.md](sources.md)).
- **The uploads.** A file dropped on a field goes to `uploadFile`; the field shows its busy state while the upload is in flight, then the stored file, or `uploadFailed` when the upload rejects. Dropping another file at the same field clears the failure, and so does any write that changes the file there, to another file or to none: a file chosen from the team's files, a typed link, a clear, a list's sheet filling the row, the host's own `setValues`. The failure then leaves the hook's `failedUploadIds` as well as the screen, so a field mounted again over that id shows no failure under the file that replaced it, while a write that leaves the file as it was, such as another input or a row added after the failed one, keeps it. An upload that fails after another file was written in its place while it was in flight marks nothing, for the same reason. The newest file at a field wins over an older one still in flight, and a successful upload writes its file over whatever was written there meanwhile.
- **The rows of a list.** A list's remove button goes through `removeItem`, so removing a row moves a failed upload's mark, and an upload in flight, along with every row it renumbers: with `[A, <failed upload>, C]`, removing A leaves the mark on the failed row and shows nothing under C. Removing the failed row itself ends its failure. The host's own `setValues` is read by position, and a host that moves rows itself uses `removeItem` and `moveItem`, after which each moved row keeps its controls on screen as it does after the list's own remove button ([upload-seam.md](upload-seam.md#what-the-form-keeps-by-id-moves-with-the-rows-it-moves)).
- **A row's layout.** A row holding a single value keeps its input beside the row's number and its remove button. A row holding a structure puts the number and the button on a line of their own above its fields, so the fields take the row's whole width: beside the button, every input of a traveller or a line item ended a button short of the row's edge, which on a phone, where the button is a 44 pixel touch target, was a third of the row.
- **Several files at once.** With `uploadFile`, a list of files offers a drop area for several files, with nothing to wire. The list writes its new rows through `setValues`, which commits at once, so each `dropFile` that follows sees the row it is handed, and each upload writes its file at its row's id when it lands, whatever order the uploads finish in. Several uploads may therefore be in flight in one list, and `uploading` and `ready` wait on every one of them ([upload-seam.md](upload-seam.md#a-list-of-files-takes-several-files-at-once)).

Its props are the form's environment: `disabled` (while a run is in flight), `allowUrl` and `resolveUrl` (the upload seam's), `loadBytes`, `pdfWorker` and `openExternal` (the result view's file settings, which draw a PDF in its field page by page and open its links, [upload-seam.md](upload-seam.md#what-a-files-preview-paints-from)), `loadText` (which lets an input holding a stored text be edited, [stored-values.md](stored-values.md)), `errors`, `foldOptional`, `framed` (the host's panel around the form), `className` for the stack the fields sit in, and three optional providers it mounts around the fields when given, `locale` and `strings` (`FieldStringsProvider`, [i18n.md](i18n.md)) and `presentation` (`FieldPresentationProvider`). Without them it reads the nearest providers above it.

## What the method's meaning changes

MTHDS `9.2.0` lets a method say what its fields mean, and the form reads every such fact from the descriptor, never from a value or a field's name ([wire-correspondence.md](wire-correspondence.md)). A method that says none of it gets the form it always got.

- **The role layout.** When some input states a `role`, the subject comes first, the context and guidance follow in their authored order, and the references and settings fold behind a disclosure of their own after every other input ("Show 2 references and settings"). An input with no role then takes the standard's default: a file is the subject, an optional prose is guidance, an optional choice or number is a setting, and anything else is context. A reference or setting the run waits for, with no default to fill it, stays with the main inputs, because a run must never wait on an input that is out of sight. The folded group opens by itself when one of its inputs is newly refused after an attempt or newly carries a host's `errors` entry (a server's verdict), so a mark is never first drawn out of sight; once open it is the person's to close, it stays open after the value is put right, and its Hide button closes it even while a mark stands. An optional structure never folds by its role: it already folds behind the optional disclosure, which is what opens it seeded with its authored defaults and closes it again. In a framed form the group's disclosure and inputs are children of the form itself, so the section rules separate them as they do every other input. A host's `order` still applies over the role order, since a host states it for a reason the method cannot. With no role stated anywhere, nothing reorders and nothing folds beyond the optional disclosure.
- **A number's entry.** A `rating` whose bounds are whole and at most ten apart is a row of steps ("4 out of 5"). Any other number with both bounds gets a slider beside its input, unless the method calls it a `quantity` or counts it in a currency, where a slider would make an exact value a hunt and the stepper stays. A `unit` is drawn beside the value: a currency's symbol where the reader's locale writes it (`€` before the amount in English, after it in French), `%` after a percentage, a unit of measure's symbol (`m²`, `kg`) after the number; the range hint under the label is written in the same unit. A slider that holds no value yet rests at its minimum faded and is announced as "Not set", and a press or a key on it sets the value where it rests, so the minimum can be picked. A slider's step is derived from its bounds: a power of ten no coarser than a hundredth of the span and fine enough that both bounds are steps, so `0..0.05` slides and `0.05` reaches `1`; a whole number steps by one and a currency by a hundredth. A rating holding a value between two steps (`3.5` from a default, an example or a restored run) shows it as a step of its own, chosen, in its place. The stepper rounds each step to the step's decimals, so `0.1 + 0.05` stores `0.15`, never `0.15000000000000002`, and never lands on an excluded bound (`exclusive_minimum`, `exclusive_maximum`): it stops one step inside.
- **A text's input.** A `format` picks the browser's own input and keyboard: an email and a web address get theirs, with spelling help off; a `time` is the browser's time picker, stored as `HH:MM:SS` because the format requires the seconds; a `date-time` is the browser's date and time picker, stored as RFC 3339 with the browser's own offset so the instant survives a server in another time zone, and a stored value is shown as the same instant in the browser's zone, or, when it carries no offset (a bare `2026-11-28` included), as the wall time it states, never read as UTC; what the person types is kept in the input as typed while the value stands for it, so a year typed digit by digit is not rewritten under them; a local time the clocks skip that day (02:30 on a spring change) is refused with the field's own problem rather than stored as another instant; a restored time carrying a zone (`14:30:00Z`, `14:30:00+01:00`), which a time picker cannot show, keeps a plain text input where it is seen and edited as it is; a `uuid`, `hostname`, `ipv4` or `ipv6` is set in monospace with spelling help off. A prose slot with a format is one line, since the engine makes every `native.Text` slot `prose` and the format is what says it is short. A `max_length` draws a counter under the input, counted in code points as the gate counts them, announced to a screen reader once the text nears the cap.
- **Examples.** A slot's `examples` are chips under its control, "Examples: €250.00, €1,200.00"; picking one fills the field with it, never starts a run, and asks nothing, because an example is a value the person can see and change.
- **Described options.** A choice whose options carry a `description` is drawn as cards, each with the option's label, its description, and the dot of its `tone` when any option has one; an option's authored `label` replaces the worded code in both presentations, and two options the method labels alike are each said with their code beside the label ("Basic (Basic monthly)"), as two worded codes that collide fall back to the codes.
- **The intents.** `code` sets a prose input in monospace, without spelling help or wrapping; `identifier` does the same for a one-line input; `question` makes the input the composer of a chat-like page, taller and larger, asking for the question. On a file input, `photo` and `scan` offer the camera first, above the drop zone ("Scan pages" for a scan, named "Scan pages for" the field's label, as "Take photo for" names a photo's), on a touch screen only as the camera always is ([camera.md](camera.md)); `screenshot` adds a "Paste a screenshot" button beside the drop zone, and pasting into the field works too. A pasted picture is named after the field's label, with the characters a file name cannot hold made dashes, and the extension its type is saved with (`svg` for `image/svg+xml`, `jpg` for `image/jpeg`). The note under the button says the clipboard holds no picture, or that the browser did not let the page read it, and goes as soon as a file arrives some other way.
- **Values checked before the run.** Readiness checks a filled value against the facts its method states, the same way the run gate does: a number's bounds, inclusive and exclusive, and whether it is whole; a text's lengths, its `pattern` (with the gate's `u` flag) and its `format` (with the gate's own format table). An input whose value breaks one counts as missing, so the Run button waits, and after `attempt()` it carries the problem in words ("Must be an email address.", "At most €50,000.00.") through the `invalid` arm of `gateRefusal`, inside a structure as at the top level, and on a list by the first refused item's position ("Item 2: Must be at most 10."). A method's `pattern` is the one fact readiness leaves out: it is the method author's regular expression, one with catastrophic backtracking would freeze the page on every keystroke, so it is judged at the attempt, where the gate judges it, and named then ([run-gate.md](run-gate.md#a-value-that-breaks-its-contract-facts)).

## What stays the consumer's

The run button and what it does, the panel and its layout, the run history, a heading or an introduction, the choice of method, where files are stored (`uploadFile`), which stored files a person may choose from (`fileSource`, which only lists them: choosing one writes its reference into the form and changes no stored file), which examples a person may see, whether they may open, rename or delete them, and what a row says of each (`exampleSource`), how a stored reference previews (`resolveUrl`, `loadBytes`, `pdfWorker`), and anything specific to one method: which slot takes only PDFs, which child is never sent, what order a team fills the inputs in. Those last three are `prepareFields` and `order`, so a host states them as data and the form applies them.

## Relation to the story harness

`MethodForm` was promoted from `src/__stories__/case-form.tsx`, the harness every per-control story renders through. That harness stays: a control story drives states that a form owns itself (an upload in flight, a failed one, an error) from its arguments, which a real form must not take from outside. `Inputs/Method Form` holds the stories of the whole form.
