# The run gate

A run has two verdicts on it, and they are not the same call.

**In the browser**, `computeReadiness` decides whether the Run button is live. It answers one question — is every input the run needs actually there? — over the descriptors the form is rendering.

**On the server**, `gateRunInputs` decides whether the run may start. It is a strict *superset*: it validates shapes against the contract's JSON Schemas and builds the wire payload, on top of asking readiness's own question. That asymmetry is deliberate. A run endpoint is public, the browser's checks are trivially bypassed, and the server is the trust boundary; readiness is UX.

What the two must never do is **disagree about whether an input is there**. When they do, the form offers a run its own gate refuses — or, worse, the server starts a paid run behind a button that was disabled. Every bug this package has shipped in that family had the same shape: two pieces of the kernel answering "is this input present?" differently, with no host able to correct it from outside.

## Use `gateRunInputs`

```ts
import { gateRunInputs, getPipeIOContract } from '@pipelex/mthds-form';

const contract = getPipeIOContract(PIPE_IO_CONTRACTS, 'quotes', 'extract_brief');
if (!contract) return notFound(); // no such pipe in these contracts
const gate = gateRunInputs(contract, requestBody);

if (!gate.ok) {
  // gate.missingInputs — variable names the caller left empty or short
  // gate.errors       — RunInputError[], when the scan cannot name anything
  // gate.preparedData — the repaired data the verdict was reached on
  return reject(gate);
}
await startRun(gate.inputs);
```

`data` is typed `unknown` because that is what arrives at a public endpoint: no framework enforces a declared parameter type, so the argument is whatever the caller put in the body. Normalizing it is the gate's first step rather than a wrapper around the gate — a `null` body would otherwise throw *after* validation had already judged it, past the point where a verdict could come back.

The result is a verdict, never a throw. A rejection is an ordinary outcome here, and frameworks routinely strip a thrown message to an opaque digest in production builds.

## Why the assembly is the kernel's job

The gate is four exported steps — `buildRunInputsSchema` → `prepareRunInputs` → `validateRunInputs` → `apiInputsFromSchemaData` — and they stay exported, because a host rendering its own panel needs the schema or the verdict on its own. But **assembling them is not a host's job**, for two reasons that are invisible until they bite.

**The schema is not the whole rule.** The schema's `required` asserts only that a key is *present*, and a content model carries no `minLength`. So a required input that arrived empty — `{document: {url: ""}}`, `{text: {text: ""}}` — satisfies the schema. That is the natural payload, not a contrived one: `rjsfDataFromRunValues({}, fields)` emits exactly that when nothing is selected. Without a re-check the server would be *more permissive than the button in front of it*.

**Picking the re-check is where it goes wrong.** There are four look-alike predicates, and only two of them are the ones the Run button reads. The obvious pair, `inputMustBeFilled` + `isFilled`, agrees on every native concept and diverges on a structured one **in both directions** — `isFilled` on an object is `some(child filled)` where `fieldFilled` is `every(required child filled)`. That accepts a half-filled struct the browser refuses (a paid run past a disabled button) *and* rejects a filled all-optional struct the browser accepts. A host whose methods happen to use only native concepts has no test that can catch either, which is exactly the position a host is in on the day it adopts.

`gateRunInputs` runs `computeReadiness`'s *own* two functions, **and over the same selection**, so the rules are shared by construction rather than by resemblance. (The tree they run over is the gate's own — a private structural walk of the contract's `json_schema` in `gating-fields.ts`, because a server must never need the wire input-form descriptor the browser's render tree is mapped from; agreement between the two trees is what `gate-agreement.test.ts` asserts. That walk follows `$ref` with a per-path cycle guard: a self-referencing model degrades to an opaque leaf instead of overflowing the stack — open by design, because the validator resolves recursion natively and has already enforced *presence* of required children at every depth; presence is all it enforces, though, so a required scalar that arrives present-but-blank below the cycle point is caught by neither side — a recorded residual, not a safety property — while a definition merely referenced from two siblings still expands in full.) The selection is the half that is easy to leave out: sharing `fieldFilled` and `mustBeFilled` but keeping only the inputs the method *demands* still lets a touched optional input through, because the check it would have failed is never run on it. [`src/core/__tests__/gate-agreement.test.ts`](../src/core/__tests__/gate-agreement.test.ts) asserts it by running both sides over one table — including the structured fixtures a host does not have — which is the only form of that claim worth trusting.

## Which `*Filled` to reach for

| | |
| --- | --- |
| `computeReadiness(fields, values)` | the answer for a **form** — is the Run button live, and what is still missing |
| `gateRunInputs(contract, data)` | the answer for a **server** — may this run start, and what is the payload |
| `isFilled(value)` | the **leaf** predicate: is there anything here at all? The one to reach for outside gating — deciding whether an optional section starts folded, say |
| `fieldFilled(field, value)` | `isFilled` applied to one descriptor, honouring what that field's concept demands inside it (required children, a declared item count) |
| `mustBeFilled(field)` | whether a field gates at all — reads the `gating` the wire carries on the render tree, and the one the gate's own tree stamps from the contract |

`isFilled` stays exported because its standalone use is legitimate. The other two are exported because `computeReadiness` is built from them and a bespoke surface may need the same pieces. None of them is a server gate, and hand-assembling one out of them is the mistake `gateRunInputs` exists to remove.

## What counts as present

The rule is one predicate, `isFilled`, read in three places — the value bridge, the payload builder, and `fieldFilled` — and shadowed by the prune's own, strictly narrower test, `isEmptyAfterPruning` in `wire-format.ts`. The prune counts as empty only `''`, `null`, `undefined` and an object that pruned down to `{}`, and it never drops a required key, so an array of any content, a whitespace-only string and a file shell such as `{url: ''}` all survive it although `isFilled` reads each as blank. The difference runs one way only: nothing the prune drops is filled by `isFilled`'s measure. A change to `isFilled` does not reach the prune by itself. [architecture.md](architecture.md) § "What absence looks like" states it in full. Three consequences are worth having in front of you when reading a verdict:

- **A structure must be touched.** An input the method demands is missing until a value goes somewhere inside it, even when its concept declares no required child. Opening the section is view state the value never sees. That shape draws an advisory `input_presence_vacuous` warning from pipelex's validate surfaces, so a form mostly meets it from a method authored despite the lint — and both halves of the kernel still answer it the same way when one arrives.
- **A touched *optional* input is held to its concept, on both surfaces.** It is out of the reckoning while untouched and in it the moment something is filled. So the readiness count moves from 3 of 3 to 3 of 4 when the user starts filling an optional structure, and to 4 of 4 when they finish — and the gate applies the same rule to the same inputs, which is not something the schema can do for it: a required child that is a plain string arrives as `''` and satisfies `required`. The rule stated properly is that the gate holds to its concept exactly the inputs it is about to put on the wire, and nothing it will omit — the payload builder tests the very same `isFilled`.
- **A declared item count gates, at both ends.** A `Concept[N]` list is satisfied only by `N` filled items; a variable `Concept[]` list never gates, because its empty form is the legitimate value `[]`. The bounds reach the descriptor as `ListRunField.itemCount` and `maxItemCount` — on the render tree from the wire's `item_count` and the schema's `maxItems`, on the gate's own tree from the same `minItems`/`maxItems` the validator reads — separately, because they are two facts. Too many items is not filled either: the control will not add past the upper bound, so that answers a list which arrived from somewhere else, and calling it *missing* stretches the word a little rather than letting the button offer a run the validator refuses on `maxItems`. Each bound is asked on its own, so a model that states only a ceiling gets one enforced — a nested array inside a structured concept may declare either alone, and a bound the descriptor publishes and nothing reads is a bound only the validator holds.
- **A started list row owes its concept the same as a touched input.** One level down from the rule above, and for the same reason. `isFilled` on an array is `some`, so a row holding `{name: '', notes: 'a thought'}` reads filled while the child its concept requires is blank — and the validator agrees with it, because `''` is a present string. A row the user has put something in must therefore satisfy `fieldFilled` for the item, exactly as a touched optional input must. A row that is empty stays an absence for the purpose of *gating*: an untouched row blocks nothing, and a variable list still never gates on being empty. Note what that does **not** say — an untouched row alongside a filled one still travels, as the shell the bridge built for it (`{name: ''}`). Only a list with no filled row at all deflates away entirely. The asymmetry is deliberate for now and is the open decision L-260929-1abc53: dropping empty rows from a mixed list is a change to what goes on the wire, and it has to be decided together with the other absence questions rather than slipped in beside a readiness rule.

## A value that breaks its contract facts

A method's contract facts (MTHDS `9.2.0`: a number's `minimum`, `maximum`, `exclusive_minimum` and `exclusive_maximum`, a text's `min_length`, `max_length`, `pattern` and `format`) ride the input-form descriptor and the contract's schema both, so the form and the gate each read them from their own artifact. `fieldFilled` asks `valueProblem` (`src/core/value-checks.ts`) of every leaf it finds filled, so a value that breaks a fact counts as missing and the Run button waits, exactly as the gate's validator refuses it. The two halves agree because `valueProblem` uses the validator's own rules: lengths counted in code points (`codePointLength`, as the validator's `ucs2length`), a pattern compiled with the `u` flag, a format checked against `schema-formats.ts`'s table. `src/core/__tests__/value-checks.test.ts` runs both halves over one table, as `gate-agreement.test.ts` does for presence.

The check is never stricter than the gate: it reads only what the descriptor states, and the engine projects each of those facts into the schema the gate validates. An invalid value in an optional input is refused as well, since the gate holds a touched optional input to its concept. `gateRefusal` names the refusal `invalid`, for a leaf and for a list holding a refused item, and `refusedValue` locates it (the leaf's own problem, or the list's first refused item with its index), which a form words with `locatedProblemMessage` ([method-form.md](method-form.md#what-the-methods-meaning-changes)). `waitingFields` carries the same `problem` on a field the run waits for, so a composer says what to fix rather than what to fill ([generative-ui.md](generative-ui.md)).

**A method's `pattern` is judged at the attempt, not on every keystroke.** A pattern is the method author's regular expression, and JavaScript cannot interrupt one: a pattern with catastrophic backtracking (`^(a+)+$` over forty `a` and a `b`) runs for seconds or longer, synchronously, on a value a person can type. Readiness answers on every keystroke, so `fieldFilled` reads every other fact and leaves the pattern out (`valueProblem(field, value, { patterns: false })`), and so does `waitingFields`. `gateRefusal`, which a form asks once a run has been attempted, reads it, as does the gate's validator itself; a verdict is cached per pattern and value, so a re-render that asks again about the same value does not run the expression again. Leaving it out makes readiness looser than the gate on a pattern, never stricter: the Run button may light over a value that breaks its pattern, and the press then names the problem on the field, exactly where the gate refuses it. A pattern that hangs still hangs the gate on the press, which is the method's own defect; what this rule removes is the page freezing while the person types.

## What arrives that nobody designed for

`gateRunInputs` takes a request body. `computeReadiness` takes a form's state. Neither is a value the controls produced, so the emptiness rule has to hold for values that were never rendered at all — and the schema is no bound on them, because `prepareRunInputs` copies a property the schema does not declare straight through. A key the validator never walks still reaches `isFilled`.

- **Depth.** The walk stops at a cap and answers `false` there. Unbounded, a value a few thousand levels deep threw `RangeError` out of the middle of a host's server gate — a gate whose whole contract is that it returns a verdict instead of throwing. The direction is the deliberate half: past the cap nothing can be told about what is down there, and an unanswerable absence fails closed like every other one here. It costs almost nothing, because `isFilled` combines branches with `some` — an over-deep branch loses its own vote and a real value beside it still reads filled — and no concept structure declares nesting anywhere near that deep.
- **A body that is not an object at all.** `gateRunInputs` takes `unknown` because a public endpoint's argument is whatever was sent. The validator is shown that value rather than a repair of it, which is what makes `must be object` a verdict a caller can actually receive; the indexing that follows uses a safe `{}` stand-in, which is what keeps the gate returning a verdict instead of throwing. Repairing *first* looks equivalent and is not, which is why it was changed: with a contract whose inputs are all optional the `required` list is empty, so the repaired `{}` validated and a string body used to come back `ok: true` on a run that carried no inputs at all. It no longer can — the validator sees the string and answers `must be object` — so a malformed body cannot start a run whatever the contract demands.
- **Cycles and sharing.** The walk keeps the objects it has already judged. That is a cycle guard and a memo at once: an object reached twice within one call answered `false` the first time, since a `true` short-circuits every `some` above it. Without it, a value shaped like a diamond chain costs exponential time. It records the **depth** each object was judged at, because a `false` here has two causes and only one of them travels: past the cap it means "could not look", so a node judged empty at the bottom of a deep branch must be walked again when a shallower path reaches it, or a genuinely filled input reads as missing depending on which branch ran first.
- **Blank strings.** `"   "` is not a value. A content model carries no `minLength`, so the validator passes it, and a required text input holding three spaces used to light the Run button and start a real run. The same test is what makes a blank *optional* input a real absence on the wire rather than a supplied empty string.
- **Names that collide with `Object.prototype`.** Every key this package indexes a record by is chosen by the method author, and the records are plain objects a host built — so `values["constructor"]` answers the inherited function, not `undefined`, and `isFilled` had no branch that called a function empty. A required input named `constructor` reported ready while holding nothing. Every such read now goes through `ownProp`, and `isFilled` answers `false` for a function as a backstop. **The validator does not close this, by design:** its `required` reads `data.constructor === undefined`, as ajv's did, and the inherited function satisfies it. The same read is why `getPipeIOContract` no longer hands back the `Object` constructor for a prototype-named pipe code — a truthy non-contract that sails through the `if (!contract)` guard a host is shown writing.

The write twin is left open on purpose and is worth knowing about: `out[name] = value` on a plain object invokes the inherited `__proto__` setter for that one name, so an input actually called `__proto__` is dropped from a payload rather than added to it. That fails loudly — the runtime refuses a run whose input is missing — where the read bug failed open, and `__proto__` is not a name an author writes.

[`src/core/__tests__/hostile-values.test.ts`](../src/core/__tests__/hostile-values.test.ts) asserts these through both halves, and [`gate-agreement.test.ts`](../src/core/__tests__/gate-agreement.test.ts) asserts the malformed-body verdicts.

## The validator generates no code

The gate validates a run's data against its schema with the package's own JSON Schema interpreter, [`src/core/schema-validator.ts`](../src/core/schema-validator.ts). **It generates no code**: it walks the schema and judges the value as it goes, builds no function from a string, and calls neither `eval` nor the `Function` constructor. So the gate runs in a browser whose Content Security Policy has no `'unsafe-eval'` in `script-src`, as well as in a worker and on a server.

That is the reason the interpreter exists. The gate used to validate through ajv, which compiles every schema into JavaScript with `new Function(...)` before it validates anything. A policy without `'unsafe-eval'` refuses that call, the refusal surfaced as one bare error carrying ajv's stack, and so a host that enforced such a policy could run no method from the form at all. Ahead-of-time compilation was no way out, because the schemas are built per method at run time, and a cache of compiled validators still compiles each schema once.

The interpreter reproduces the ajv instance the gate ran with, so the verdict did not move when the engine did:

- **every error, not the first** (ajv's `allErrors`), in ajv's order, since a host typically shows the first;
- **pydantic's lax coercion** (ajv's `coerceTypes: true`): `"20"` becomes `20`, `""` becomes `null` where `null` is allowed, a type list is tried in its own order, and the coerced value is **written back into the data in place**, which the gate relies on — the string the user typed is stored as a number from then on;
- **the formats**: the full set ajv-formats defines, RJSF's `data-url` and `color`, and the pydantic-parity `date` and `date-time` from `date-format.ts` ([`schema-formats.ts`](../src/core/schema-formats.ts));
- **the error objects**: keyword, instance path, schema path, params and message are ajv's, so `RunInputError` and every message built from it read exactly as before;
- **a malformed schema** is refused as ajv refused it, against the draft-07 meta-schema and for an unresolvable `$ref`, with one verdict-less error, and so is a schema declaring a `$schema` other than draft-07, which ajv did not know.

It leaves out what the gate never used: `$data`, remote references and `$id` below the root (a schema carrying one is refused, since its references would resolve to the wrong place), `unevaluated*`, `discriminator`, ajv-formats' `formatMinimum` family, and the warning ajv logged for an unknown format, which is still ignored. An off-the-shelf interpreting validator was the other option, and it was set aside because none reports in ajv's terms: each words, orders and nests its errors its own way, none coerces as ajv does, and their formats live in a process-wide registry, so the gate would have had to re-derive every error a host reads from another library's prose.

One limit moved, and it is the price of interpreting. The interpreter walks a value by recursing, a few calls per level, so a value nested through a self-referencing concept runs out of call stack after a few hundred levels, where ajv's compiled code lasted a few thousand. Past that point the gate refuses the run with one verdict-less error, `the inputs are nested too deeply to validate`, rather than throwing; no form produces such a value, and both validators refused past their own limit.

The property is held from several sides. [`gate-no-codegen.test.ts`](../src/core/__tests__/gate-no-codegen.test.ts) runs the gate with `eval` and every function constructor made to throw (`Function`, and the async and generator ones, reached by name or through `.constructor`), and it must still reach real verdicts. [`schema-validator.test.ts`](../src/core/__tests__/schema-validator.test.ts) holds the interpreter to a table of ajv's own answers, errors and coerced data alike, captured from the instance it replaced. `make assert-bundle` fails if anything the `.` entry reaches calls `eval`, `Function(` or `.constructor(`, and if the validator's chunk reaches any entry but `.`. Lint refuses the code-generating validators by name across `src/`.

## Schema caching

`gateRunInputs` keeps one schema object per contract in a `WeakMap`, and the validator remembers, per schema object, the verdict of checking that schema against the meta-schema. Building a fresh schema per call would repeat that check on every request — on a public endpoint, work driven by the cheapest request there is, an empty body rejected in a fraction of a millisecond. (When the validator was ajv, the stake was larger: its compiled-schema cache was keyed on schema object identity and never evicted, so a fresh object per call also retained another compiled validator.) Both maps are weakly keyed, so neither pins a contract or a schema that goes out of scope.

## Rendering the rejection

The verdict is the contract; its rendering is not. `describeValidationError(error, translate, gate.preparedData)` is one presentation of a `RunInputError` and a host is free to write another — it takes an injected `Translate` so the kernel stays i18n-agnostic. A consumer branches on the structured fields, never on message text.

A message that names a field names the field's **identifier** — the one written in the method — never the schema `title` a pydantic contract carries alongside it. That is the one deliberate divergence from RJSF's error transform, which substitutes the title because in an RJSF form the title *is* the rendered label. Here the controls label a field by its identifier, so quoting `'Audience'` at someone whose bundle says `audience` sends them looking for a field that does not exist.
