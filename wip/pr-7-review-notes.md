# PR #7 review follow-ups

The fourth review round against this branch, on [PR #7](https://github.com/Pipelex/mthds-form/pull/7) — the `release/v0.4.0` PR. Two reviewers, four findings, **deferred in full**: nothing reported is a regression from this branch, and nothing rose to blocking on a release PR that is green.

Three of the four are re-reports of items already recorded in [`pr-6-review-notes.md`](pr-6-review-notes.md), so this document does not re-litigate them — it points at their existing sections and records only what this round's verification **added**, which in two cases is a correction to what that document says.

## Re-reported, already recorded

**An untouched `Concept[N]?` is refused by the gate and allowed by the button** — reported by Codex on `src/core/contracts.ts:175`, the `isOptionalInput` early return in `inputMustBeFilled`. Recorded at [`pr-6-review-notes.md`](pr-6-review-notes.md) § "An untouched `Concept[N]?` is refused by the gate and allowed by the button", where it was found by the PR #6 invariant table rather than by a reviewer. **Confirmed again**, reproduced end to end: with `shots: Image[3]?` untouched, readiness reports nothing missing so the Run button is live, while the gate returns `ok: false` with `missingInputs` empty and ajv saying `must NOT have fewer than 3 items`. Pre-existing, and it fails closed — the gate is stricter than the button, so no wrong run is billed.

**A row's identity shifts when a host refuses the removal it was told about** — reported by Codex on `src/react/list-field.tsx:64-65`. Recorded at [`pr-6-review-notes.md`](pr-6-review-notes.md) § of the same name, where it arrived with the triage rather than on a thread. The mechanic is real and was re-verified: `removeItem` (`:64`) drops the local key before calling `onChange`, and `useRowKeys` (`:212`) then takes its grow branch when the array does not shorten. What this round settles is that **no path inside the package reaches it** — `ListField` is strictly controlled (`:52`), the bounds work gates **Add** only (`:85`, `:158`), and Remove is disabled only on `disabled || busy` (`:146`) — so the trigger is a host ignoring an `onChange`, which [`docs/upload-seam.md`](../docs/upload-seam.md) § "A row is a thing, not a slot" places outside the published contract.

**`specifiersOf` reads an `import()` inside a string or a comment as a real chunk edge** — reported by Codex on `scripts/assert-bundle.mjs:30`. Recorded under [`pr-6-review-notes.md`](pr-6-review-notes.md) § "Third round". Still true of the regex at `:33`, which is unanchored where its two siblings are anchored to a statement boundary — deliberately, since `import()` is an expression that may sit mid-line. What this round adds is the measurement: **`dist/` contains no occurrence of `import(` at all**. tsup externalizes `dependencies` and `peerDependencies`, so no third-party source is ever read; `graphOf` follows only relative specifiers, and every one of those in `dist/` is a `chunk-*.js`; declaration files, where `import('…')` type syntax is routine, are never scanned; and the entry glob is single-level, so `__tests__/` — the only place in `src/` with that text — is never bundled. The one live vector is a hand-written comment or string literal in this repo's own entry sources, and it fails loud in the safe direction: an over-inclusive matcher can only over-report, never let a budget violation through.

## What this round corrects in `pr-6-review-notes.md`

**The file-field replacement path Greptile reports is foreclosed, and the recorded hazard has the opposite symptom.** Greptile reported (P1, `src/react/file-field.tsx:161-168`) that replacing an existing file makes the unbound local preview adopt the previous `value.url`, so the new file's preview disappears when the upload resolves. That requires a drop while `value.url` is already set, and there is no such door: `:247` renders the dropzone only when `!hasFile`, and its input carries `disabled={busy}` (`:290`), so `handleFile` (`:121`) cannot run with a value present. Replacement goes through `clear()` (`:146`) or the URL input (`:339`), both of which call `setLocal(null)` first. The ordering it worries about — uploading cleared before the URL is written — is exactly what the `!value?.url` disjunct at `:166` is for. And there is no immediate preview to lose: `previewSrc` is painted only behind `previewOpen`, which defaults false (`:104`), so the object URL's only job is making the *first* Preview click instant. This **bounds** § "A local file preview outlives a value the host replaces mid-upload": that item is real, but it is host-triggered only, and its symptom is a chip naming one file over a preview of another — not a preview vanishing.

**`statementsOf` does not strip strings, so the third round's proposed remedy is wrong on half of it.** That section says the fix for `specifiersOf` is "to strip comments and strings before matching, which `statementsOf` already does for the barrel check further down". It does not: the scanner tracks quotes to find statement boundaries, but inside a quote it still appends each character to the current statement (`:140`). Reusing it as-is would close the comment vector and leave the string vector open. Full coverage means generalizing it into a separate strip pass — real machinery for a state that does not occur, which is why this stays recorded rather than built.

**The gate fix belongs in the gate, not the prune, and the wire payload does not change.** § "An untouched `Concept[N]?`…" reasons that "the prune (or the bridge) needs to distinguish the two" multiplicities, and that the choice of where that knowledge belongs is the work. The prune is ruled out: `pruneEmptyOptionals` is handed only a schema and has no way to see `presence`. The smallest correct site is one step inside `gateRunInputs`, between `prepareRunInputs` and `validateRunInputs`, dropping top-level keys where `isOptionalInput(input) && !isFilled(value)` — the same test `apiInputsFromSchemaData` already applies at `gate.ts:190`, and it restores the sentence the gate already claims for itself, that it holds to its concept precisely the inputs it is about to put on the wire and nothing it will omit.

**The wire payload is byte-identical either way** — checked by building it with the empty arrays present and with them dropped. The optional-unfilled arm omits them regardless, and a *plain* plural re-materializes `[]`. So this is not a wire change, which removes the reason it looked like one. What it changes is **verdicts**: an untouched `[N]?` becomes runnable with the input omitted, and, more broadly, optional inputs the payload was always going to omit stop being validated at all — a whitespace-only optional value among them. That widening is what still deserves a design pass, and it is a smaller and better-defined question than the one the third round left open.

The failing test is one row in `ROWS` in `gate-agreement.test.ts`, beside the existing optional-fixed row: `{ label: 'an OPTIONAL fixed list of three, untouched', inputs: { text: TEXT, shots: OPTIONAL_SHOTS }, values: { text: 'hi' }, runnable: true }`. Today `buttonLive` passes and `gate.ok` fails, which puts the whole invariant breach in one assertion. An `optionalFixed(count)` helper alongside `plainFixed` in `contract-fixtures.ts` would be the tidy companion.
