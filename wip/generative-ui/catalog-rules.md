# Where the designer's prompt comes from, as of 2026-09-17

`methods/layout-design.mthds` is the prompt — the brief's template and two prompts, under one main pipe. `design_layout` is a `PipeSequence` of `render_brief`, `plan_page` and `emit_page`. `render_brief` is a `PipeCompose` in template mode: a Jinja2 template over the brief as data, with no model behind it, that lays the page's half of the prompt out as Markdown — the heading naming the page and its pipe, the state and every path in it one line each, what is delegated, and on an input page the defaults and the control that runs the method, on a result page the state of one real run. Its text is what the two model stages read under `@brief_text`. Each of those carries its role in `system_prompt`. The planner's `prompt` holds the state contract in plain words, the design direction, the component list by name and description, the planning rules, the creative-seed procedure, and the tail that interpolates the laid-out brief and the guarded seed; its output is a `PagePlan`, a structure the bundle declares. The builder's `prompt` holds the output format and its example, the state contract with its syntax, the dynamic-lists and dynamic-props sections, the plan rendered by Jinja2 loops, the execution notes, the component list with every props signature, the action list, the events and visibility sections, the numbered rules, and the laid-out brief. There is no TypeScript that renders a prompt string or a sentence of the brief; improving a prompt is editing that file with `/pipelex:pipelex-edit`, and a change to a contract is `/pipelex:pipelex-design`.

The method takes `catalog = "Catalog"`, `brief = "Brief"` and `seed = "Text?"`, and the seed reaches the planner only: the plan is where two runs of the same brief diverge, and the builder follows the plan. Until 2026-09-17 the brief arrived as `Text`, a Markdown string `renderInputBrief` and `renderResultBrief` concatenated in `src/generative/brief.ts` — the last prose a model read that was written in TypeScript. Earlier, on 2026-09-16, the method was one `PipeLLM` asked for the whole page in a single completion, and until that day it took `catalog_rules = "Text"`, a twenty-thousand-character string `catalogPrompt()` rendered in `src/generative/schema.ts` by pushing lines into an array — the design direction, the rules and the seed procedure lived in three TypeScript modules, and json-render's `formatZodType` was reached only through its `promptTemplate` hook. The record of those arrangements is this file's history.

## What is data, and who supplies it

`designerCatalog()` in `src/generative/designer-catalog.ts` builds the `catalog` input: for every component in `COMPONENT_NAMES` order, its name, its props signature (`src/generative/props-signature.ts`, held by test to the text json-render's own prompt would render), its description, whether it accepts children, its named slots and its events; then the four built-in actions from `src/generative/schema.ts`, marked built-in, and the catalog's own `run`. The component descriptions still live where they did — the shadcn subset in `src/generative/shadcn-definitions.ts`, our own in `src/generative/components.ts`, the product-page components in `src/generative/catalog.ts` — and the method lays the lists out with two Jinja2 loops, so a component added to the catalog appears in the prompt with no change to the method.

`inputBrief` and `resultBrief` in `src/generative/brief.ts` build the `brief` input the same way: the descriptor projected into the method's `Brief` structure — which page and for which pipe, every path flattened in reading order with its depth, its kind in words (`kindLabel`, the one exhaustive switch over the descriptor's kinds), its constraints in words, whether the kernel keeps it, what gates the run, the control that runs the method (`run_control`, so the method's prose can go on naming none of the chrome), and on a result page one real run's loaded state as JSON. A list's item is described on the list's own entry (`item_kind`, `item_description`, `item_laid_out`) and its members follow with `relative` set, spelled from one item — flat, because the runtime refuses a structure that nests itself. The words a model reads about any of this are the template's.

The fixtures harness hands both values over through `scripts/pipelex/layout-design.ts`, the typed call site `/pipelex-integrate` wrote over the method's signature: as `{ concept: DESIGNER_CATALOG_CONCEPT, content: serializeCatalog(designerCatalog()) }` and `{ concept: DESIGNER_BRIEF_CONCEPT, content: serializeBrief(brief) }`, each validated against the bundle's own schema — `src/generated/layout-design/`, a projection of the bundle, refreshed with the same skill after any edit here, and `make codegen-check` says when that was forgotten — before the run is paid for, beside the bundle as `mthds_contents`. `DesignerCatalog` and `DesignerBrief` are those generated types. The call site reads two intermediates back out of the run's working memory: the plan, and the brief as the run laid it out, which the specs pass compares with the brief on record. A host does the same with its own client.

## What is prose, and why it is in the method

Everything that names a component — the direction's advice on which control to reach for, the rules about Tabs and Steps — is the method's own reading of the vocabulary it was written for, and stays beside the rest of the prompt rather than travelling as data. The split is deliberate: the method is coupled to no catalog *listing*, and the prose that assumes this package's components is in the one file a person edits to change what a page looks like.

The product chrome — `AppBar`, `Hero`, `Workspace`, `Section`, `Rail`, `SummaryRow`, `Cta`, `Footer` — is the exception in the other direction: the method names none of it, and `prompt.test.ts` holds it to that. Until 2026-09-16 the prompt carried a product-page grammar (a hero, numbered sections, a rail of summary rows ending in the call to action, a bar and a footer) in the planner's direction, its rules, the plan's structure and the builder's rules, and every captured layout had the same skeleton; Louis asked for the composition to be the model's alone. A rule that names a `Rail` is a composition, so what those components are for lives in their catalog descriptions in `src/generative/catalog.ts`, which say what a component is and how it renders — a heading level, a landmark, a fixed child count — and never where it must go or whether a page must have it.

Three things to know before editing the prose. A literal dollar sign is written `$$`, because `$name` is the language's inline substitution and every json-render expression key (`$$state`, `$$bindState`, `$$item`, `$$cond`, `$$template`, `$$or`) would otherwise be rendered as a variable and refused at load — in the brief's template as much as in the prompts. In the two prompts, which keep every newline they are written with, a loop body ends with its own newline, so the heading that follows a loop sits directly under `{% endfor %}` to render one blank line rather than two. The brief's template is a `markdown` template, and that category trims a line holding only a `{% %}` tag, so its loops and conditions sit on lines of their own; a line that ends with such a tag closes it with `+%}` to keep its newline, and every `{% set %}` sits at the top of the template — the runtime's variable detection reads a name set inside a loop or a condition as an input the pipe never declared, and refuses the method with `Required variable 'x' is not in the inputs of PipeCompose`.

## Reading the rendered text

Every file under `wip/generative-ui/briefs/` carries the hero's brief as the method's `render_brief` stage laid it out, then the brief data and the catalog data as JSON, and the prompt hash; the method file it names is the rest. `make briefs` regenerates them from the committed fixtures, laying each brief out through the local runtime (`scripts/render-briefs.py`, over the sibling `../pipelex` venv) so the text is the runtime's own rendering. The diff taken on 2026-09-17 against the last TypeScript-rendered briefs was byte-identical on six heroes; on the seventh, `results.deep_result`, the two nested item lines gained the item's description in parentheses, which the old code printed at the top level only. To read the two prompts exactly as the runtime renders them, run each stage's `system_prompt` and `prompt` through the runtime's own preprocessor and Jinja2 environment over that JSON, with a sample plan for the builder's — the diff taken on 2026-09-16 against the last TypeScript-rendered prompt showed every component line, rule and direction paragraph byte-identical, the role line moved to `system_prompt`, one duplicated sentence dropped from rule 13, and `Collapsible` listed one place later, in the catalog's stated order rather than the definitions file's.

## The trap

`src/generative/prompt-hash.ts` pins the first twelve hex digits of the SHA-256 of `promptHashSubject(method, catalog)` — the method file's text, then the catalog data as JSON. Editing a paragraph of the method, a component description, a prop, or the model pin changes the hash, and both the briefs pass and the specs pass refuse to run until the pin is updated — which is deliberate, because a captured spec is only meaningful against the prompt that produced it, and every capture has to be re-run. `src/generative/__tests__/prompt.test.ts` recomputes the pin and reports the new value.
