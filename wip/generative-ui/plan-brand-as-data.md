## The plan

**Written 2026-09-03 on Louis's redirect, ratified by him the same day; continues on this branch, in this worktree.** The use case, in his words: a person has built a method that implies an input form, and to put their brand on it they hand over a logo, a colour palette, a font, whatever can be pulled off their website; what renders in Storybook is that brand on the method's page. The rule that governs the phase: **the model writes data files only.** No TypeScript, no CSS. Each file is validated against a schema and recorded with its producer, exactly as the layout spec is. Anything the data cannot express is not on the page: the blur orbs, the canvas gradient and the hand-written `pipelex-brand.css` of the prototype go, and nothing replaces them by hand.

### The two artifacts of a brand

Beside the layout spec per method, two files per brand under `data/brands/<slug>/`, with the producer's JSONL beside them as the specs pass does:

- **`tokens.json`, DTCG.** The theme contract as tokens, each with a `light` and a `dark` mode (Terrazzo's `$extensions.mode`): the shadcn semantic colours the controls read (background, foreground, card and its foreground, popover and its foreground, primary and its foreground, secondary and its foreground, muted and its foreground, accent and its foreground, destructive and its foreground, border, input, ring), the radius, the font families (sans and mono), and a shadow only if a control or a brand component consumes one. Colours in any DTCG colour space; the build decides how they are written.
- **`brand.json`, the manifest**, validated by a zod schema written once: the brand name, the website it was read from, one logo URL per scheme (light and dark), and the font source when the family is a webfont the host must load (a Google Fonts family name, or none). A URL and a name are data; a `<link>` and an `@font-face` are the host's, written once.

The contract the producer writes against is generated, never hand-written: `make briefs` gains `wip/generative-ui/briefs/brand-contract.md`, the list of token ids with what each one paints, rendered from the same table the theme reads, so the producer and the build cannot disagree on a name.

### The pipeline, ours, written once

`scripts/build-brands.mjs`, run as `make brands`: for each brand, `@terrazzo/parser` parses and lints the tokens (both modes required, every colour valid, no duplicate values, descriptions present), `@terrazzo/plugin-css` emits the custom properties with `modeSelectors` for `.dark` and variable names that ARE the theme contract's, scoped under `.brand-<slug>`, into `src/__stories__/_generated/brands/<slug>.css`, committed like the specs modules. A brand that fails validation gets the repair loop the specs have (the validator's messages back to the producer, a bounded number of rounds, every round recorded) and, past the bound, a rejected file beside the brief. The Terrazzo packages are devDependencies imported from the story tree and the scripts only; `docs/dependency-budget.md` records them, and `make assert-bundle` keeps proving nothing reached the entries.

**The one package change, and the prerequisite for all of it: the theme contract moves from HSL triplets to full colours.** `src/styles/theme.css` states `--primary: #00bb95` (or an `oklch()`), and `@theme inline` in `src/styles/tailwind-entry.css` maps `--color-primary: var(--primary)`. This is modern shadcn's own convention under Tailwind v4, a contained edit to two files and to `docs/theming.md`, and a breaking change for hosts that set the triplets, noted as such in the changelog. It is done first, on its own commit, with every gate green, because nothing in the phase works without it and because it must be judged on its own.

### The producer

A Pipelex method, `brand.tokens_from_site` in `data/generative/`, on `claude-4.8-opus` and nothing else in this phase: the phase compares nothing, it proves one path. Its inputs are the brand contract (the generated brief) and **site facts**: what a script pulled off the website deterministically, `scripts/extract-site-facts.mjs`, which fetches the page and its stylesheets and records, as data, the colour scheme, every colour custom property and the colour utilities by frequency, the font families and font links, the radii in use, and the image candidates for a logo. The method's judgment is the mapping, which colour is primary and which is the surface, what the light mode of a dark-only site is, and it writes the two files. Provenance is the specs' record: producer, model, date, the hash of the brief. The first brand is Pipelex, from pipelex.com, because the facts were already read by hand on 2026-09-03 (`temp/generative/prototype/pipelex-design-system.md`) and the script must reproduce them; a second, light-first site is run only if the first holds, to show the mapping is not tuned to one page.

### The rendering

The prototype page, re-based on the data: the brand components keep their structure and lose their hand styling (the `Logo` reads the manifest through a brand provider and carries no URL in the spec, `AppBar`, `Hero` and `Glass` paint from tokens only), the kernel controls take the tokens as they do today, and the story becomes one per brand, `Generative/Brand/<name> · trip planner`, titled with the producer, rendered in both themes by `ThemePair` from the two modes of one file. The trip planner's layout spec is the one already on the branch; this phase changes nothing about how a layout is produced.

**What Terrazzo 2.7.1 actually does, so nobody re-learns it.** The JS API is `defineConfig({ tokens, outDir, plugins, lint }, { cwd: new URL(import.meta.url) })`, then `parse([{ filename: new URL('file:///tokens.json'), src }], { config, logger, continueOnError: true })` returning `{ tokens, sources, resolver }`, then `build(tokens, { sources, resolver, config, logger })` returning `outputFiles[{ filename, contents }]` in memory. The default `Logger` prints and throws on the first error; a subclass overriding `error()` and `warn()` to push entries onto an array, with `continueOnError: true`, collects every problem for a repair round. The CSS plugin takes `filename`, `baseSelector: '.brand-<scope>'`, `modeSelectors: [{ mode: 'dark', selectors: ['.dark .brand-<scope>'] }]` (marked deprecated in favour of DTCG 2025.10 resolver permutations, but working; the resolver form would need a separate token set per mode, which is a worse file for a model to write), `variableName: (token) => '--...'` and `legacyHex` (false by default, emitting `rgb(0% 73.333% 58.431%)`, `oklch()` or `hsl()` as the token's own space; true emits hex). The output is exactly the contract: a `.brand-x { --background: …; --card: var(--background); --font-sans: "Inter", …; --radius: 0.75rem }` block and a `.dark .brand-x { … }` block carrying only the tokens that have a `dark` mode. A token's `$value` is the light value; `$extensions.mode.dark` is the dark one; there is no `light` mode key, so a producer writes two values per colour, never three.

**Its edges, and the decision each one forced.** A string colour parses with a deprecation warning and an unparseable string silently becomes black, so colours are **object notation only** (`{ colorSpace, components, alpha, hex? }`; a string is accepted only as an alias `{color.x}`). An object with `hex` and no `components` passes the parser and crashes the build, so `components` are required. A colour outside sRGB crashes the CSS downsampler on a colour-space id, so `core/max-gamut: ['error', { gamut: 'srgb' }]` turns that into a lint message. `core/duplicate-values` flags an alias of a colour as a duplicate (the alias skip in that rule covers only primitive types) and a shadcn palette legitimately repeats values (every foreground on a coloured surface is white), so that rule is a **warning, recorded in provenance, never failing** — the plan's "no duplicate values" is relaxed to that, deliberately. `core/required-modes` wants `{ matches: [{ match: ['color.*'], modes: ['dark'] }] }`; `core/descriptions` works as written; `a11y/min-contrast` works and reports "Pair N failed; expected 4.5, got 1.61 (AA)", so the formatter maps N back to the pair's token names. Contrast is linted on two pairs only, foreground on background and muted-foreground on background: a brand's primary-foreground on its primary is allowed to fail AA, because pipelex.com's own white-on-teal button does, and card is allowed to be translucent glass.

**The reading against the five criteria.**

1. *Validates on the first call or after one repair round.* Met on every run. Every repair was the same fault: an alias token written with its light value only, `{color.foreground}` or `{color.primary}` with no `$extensions.mode.dark`. The contract says every colour token carries both; the model reads an alias as mode-less, which in the emitted CSS it would be, since `var(--primary)` follows the mode on its own. The one contract edit this step recommends: either say in so many words that an alias carries a dark value too, or let an alias-only token stand for both modes in the validator and the brief. 2. *Light and dark from one file, both reading as the brand.* Met on pipelex.com: the derived light mode reads as the brand, and on the rail and the inputs reads better than the hand-written one, which had made the card the canvas. 3. *Every kernel control and every brand component restyled with nothing hand-written.* Met; the page and the spec are the same in every brand story and only the data differs.
4. *Under a minute per brand.* Met when the first call validates; missed by about fifteen seconds when a repair round runs. The fix is criterion 1's.

**Findings.**

- **The cascade is a fact, and a script must compute it.** Handed every declaration of a property with its selector, the model took the first; handed the winner, it still had to be told not to prefer a value the page does not show. `asServed` is the kind of fact the extractor exists for: exact, free, and the thing the mapping most depends on when a framework's stylesheet lists a whole palette.
- **A site that shows no button has no accent to read.** On mthds.ai everything the facts state came out the same on three runs; the one thing the site never shows came out three ways. That is the limit of "the model's judgment is the mapping": where there is nothing to read, a judgment is a design decision, and it varies as one does.
- **Material's "primary" is a surface; the contract's is the accent.** The naming collision is what the third run fell into, with the contract's `paints` in front of it saying "the run button, a selected pill, a section number". A framework's vocabulary in the facts can outweigh the contract's.
- **The one-logo limit is the data's.** Both sites reference one logo file, drawn for one canvas; on the other canvas the mark is invisible, as Pause 2 predicted. Nothing on the page can invent the missing variant.
- **Low variance where the facts are explicit.** pipelex.com twice gave the same mapping within a few values; mthds.ai three times gave the same canvas, ink, hairline, surfaces, type and radius.

**For Louis's decision.** Whether tokens become the second validated artifact beside the spec. What the step showed: the pipeline holds, the derivation of a second mode holds, and the split between what a script reads and what a model decides holds exactly as far as the site shows the thing being decided. Where it does not, the answer is an input, and the use case already names it: the person hands over a logo, a palette, a font. The recommendation is therefore the smallest one, (a) a palette hint a person may supply beside the URL — the accent at least, and the logo variant the site does not reference — carried into the facts as a stated fact and recorded in the provenance, so that a brand from a site with no button is still a reading of something. The alternatives are (b) a critic round on the rendered shots, as the layout specs have, and (c) accepting the variance as a design review, as the layout specs also do. Beside that decision sits the contract edit on aliases from criterion 1, which would put every run under the minute.

**The decision — 2026-09-03, Louis, asked one question at a time.** (1) Tokens become the second validated artifact beside the spec: the path continues toward the product. (3) An alias stands for both modes: an alias token may omit its dark value and means the same alias in both modes; the validator, the brief and the test change with it, the contract hash moves, and both method brands are re-run. The order of work below gains the three steps.

## What has been seen working — 2026-09-04

Written for one question Louis asked after reading Checkpoint 7: does the system, deterministic software plus Pipelex methods and nothing else, make a method's app look like a proper web app rather than a form, with no coding agent in the loop? This section is the record of what has actually been seen working, with its evidence, and of the one thing that has not been seen yet.

**The answer, in one paragraph.** Each half of the chain has been shown to work with no agent in it, on committed data anyone can rebuild. The two halves have not yet been joined in one run: the page that reads as a product page carries a layout written by hand by a Claude Code subagent, and the layouts the method wrote were only ever painted in the stock theme. So the claim is supported for each half and unproven for the whole, and the experiment that settles it is bounded and named below.

**Working, with no agent in the loop.**

1. *From the descriptor to a laid-out page.* The descriptor comes from the runtime's own validation output, `buildRunFields` derives the fields, and `make briefs` renders the brief from them deterministically. The designer method `data/generative/ui-designer.mthds` takes the catalog prompt and the brief and answers with JSONL; `scripts/generate-fixtures.mjs --specs` compiles it, validates it against the catalog with the layer's own validator, and stores it with its provenance. The evidence is in Checkpoint 3 and Phase 5's record: every capture that returned text, across three model families through the real CLI, validated on its first call with zero repair rounds; the pages reached for the app vocabulary unprompted (a four-step wizard from `claude-4.8-opus`, `Split` rails, `Segmented` pills, `NumberInput` for the budget); the kernel's own controls held inside the model's layout for a file, a date and a list; and the readiness the kernel computes from the page's state agreed with the kernel form's on every story. The two failures on the way, the runtime's output cap on the deep hero and a per-item delegation the hatch could not yet resolve, were the runtime's and the layer's, never the model's design.
2. *From a URL to a brand.* `scripts/extract-site-facts.mjs` reads a site's facts exactly, with the cascade computed for the page as served; the method `brand.tokens_from_site` maps them onto the theme contract; `assembleBrand` validates the two files against the contract and Terrazzo compiles them into a scoped stylesheet; the page is painted from the tokens alone. The evidence is Checkpoint 7: two sites, both valid on the first call in under forty seconds, the re-skin reaching every kernel control and every brand component with no CSS written for the page, and both light and dark from one file. The person's part is the URL and, for what a site does not show, up to three stated facts beside it.
3. *Run time is model-free.* Rendering is json-render over a stored spec and a stored stylesheet, with the state loaded from the run; the split the design asked for, one generation per method version and no inference on any run, is what the harness does today in Storybook.

**Not seen yet: the join.** The product page of Checkpoint 4, re-based on tokens at Checkpoint 5 and painted from the method's tokens at Checkpoints 6 and 7, renders `pipelex-trip.spec.ts`, a layout a Claude Code subagent wrote by hand against the brand catalog with the whole repo in context. The designer method has never been handed that catalog: the specs pass renders the base catalog's prompt only, and `brandCatalog` is referenced by the authoring helper and the registry alone. So the committed branded page is method-made tokens under an agent-made layout, and the method-made layouts of Phase 5 are the pages Louis read in the stock theme as "not in the right ballpark". Nobody has looked at a method-made layout under method-made tokens, and nobody has asked the method for a page in the brand catalog's vocabulary (`AppBar`, `Hero`, `Workspace`, `Rail`, `Cta`, `Footer`).

**The experiment that settles it,** in two sizes:

- *The cheap look, no new inference.* `BrandPage` takes any spec and the brand registry extends the base one, so the trip spec `claude-4.8-opus` wrote through the method renders under either brand's tokens today. One story per brand, both themes shot. It shows whether the tokens alone turn a method-made wizard into a page that reads as the brand's, and it costs a story and a screenshot pass.
- *The real one, one inference call per run.* Let the specs pass take a catalog choice, render `brandCatalog`'s prompt with its own hash, run `ui-designer.mthds` on it with the trip brief, validate against the brand catalog, and store the fixture with `catalog` in its provenance; then a story per brand rendering that spec under the method's tokens, titled `pipelex-method` twice. If that page reads as a product page, the claim holds with no agent anywhere in the chain. If it does not, the finding is about the brand catalog's vocabulary or the direction prompt, both ours, exactly as Checkpoint 3's reading rule says.

**What stays a study.** Nothing ships; the layer is reachable only through Storybook and `make assert-bundle` proves it. The two weak spots on record are the kernel controls' own chrome inside a brand (`L-260903-7ec51b`) and a single stated accent applying to both modes (Checkpoint 7's refinement). Hosted generation and caching per method version, the `./generative` entry and the agent skill remain the follow-ups the archive plan lists.
